    Getting started

    Install the app, connect a model and start a chat. These docs describe biorouter v1.91.2 on Windows, macOS and Linux.

    Install

    Download the file for your computer from the Download page or from GitHub Releases.

    • Windows x64. Biorouter-Setup-*.exe is the installer. A later one upgrades in place and keeps your shortcuts. A .zip of the same build is also published.
    • macOS. Open the .dmg for your Mac, arm64 for Apple silicon or x64 for Intel, and drag Biorouter to Applications.
    • Linux, Debian and Ubuntu. Run this in the folder that holds the file: 
      sudo apt install ./biorouter_*.deb
    • Linux, Fedora and RHEL. Run this in the folder that holds the file: 
      sudo dnf install ./Biorouter-*.rpm
    • Linux server. The biorouter-cli packages, one .deb and one .rpm, install the command line, the background service and the browser interface with no desktop app. Install one the same way. See Command line.

    The app checks for new releases and tells you when one is ready. Settings → App → Updates shows where it stands.

    When it starts, the app checks for Git, Python, uv and npm, which some extensions use, and offers to install any that are missing. The app itself runs without them. Local models on Linux need Debian 12, Ubuntu 22.04 or newer.

    Install the command line

    The desktop app includes the biorouter command line tool, which shares your settings and chats with the app. When the command is not on your PATH, the app offers to install it as it starts. On Windows and on the Linux desktop packages, use that prompt. On macOS you can also run the bundled copy once from a terminal:

    /Applications/Biorouter.app/Contents/Resources/bin/biorouter \
  setup-path

    setup-path, which the app's prompt also runs, links the command into a folder on your PATH, such as /usr/local/bin or ~/.local/bin. On Windows it copies it to %LOCALAPPDATA%\Biorouter\bin. If the folder is not on your PATH yet, it prints the line to add. Open a new terminal and run biorouter info to check.

    After an update, the app offers to update the command when the copy on your PATH is older. The Linux server packages install biorouter to /usr/bin and need no setup.

    Connect a model

    Biorouter asks you to choose a model the first time it opens. To add or change one later, open Settings → Models → Configure providers. Providers sit on three tabs.

    • Local. Llama Server needs nothing installed. The first time Biorouter opens, its row lists models: pick one and choose Download & run. The model downloads once; after that it runs on this computer, so your messages never go to a model host. Later, Settings → Models → Local Model Inventory downloads more. Ollama needs Ollama running on this computer with a model pulled.
    • Institutional. For UCSF. Versa API Azure asks for your Versa API key. Versa API Bedrock asks for your Versa access key ID and secret access key. The endpoints are set for you.
    • Public. Claude Code and Codex use the vendor's command line tool, installed and signed in to your own plan; Biorouter never sees the credential. Anthropic, OpenAI and Google Gemini need an API key from that provider. The others ask for that provider's own key or account credentials.

    Choose a provider's row, then Configure, and enter its credentials. Biorouter checks them when you save. From a terminal, run biorouter configure and choose Configure Providers. Models and providers lists every provider and its default model, and Security explains where credentials are kept.

    Llama Server, Ollama running on this computer, and the two Versa providers are private. Ollama on another machine, and every other provider, is public. For patient data, use a private model. Once a chat uses a private model or a private data extension, it stays private, and Biorouter refuses to switch it to a public model. To change that, choose Make this chat public in Chat history, or run biorouter session declassify. See Private and public.

    UCSF researchers: use the two Versa providers on the Institutional tab. Azure OpenAI and Amazon Bedrock on the Public tab stay public even if you point them at a UCSF endpoint, because Biorouter cannot check where they send data.

    Start a chat

    1. Open a new chat Choose New chat in the sidebar, or press Cmd+T (Ctrl+T on Windows and Linux).
    2. Pick a working folder The folder chip above the text box is where the agent reads and writes files. Choose it to switch folders before you send the first message. After that the chat keeps it.
    3. Ask Type a request in plain language and press Enter, for example “List the files in this folder and summarize the README.” The agent answers and shows each tool it runs as one line.

    From a terminal, biorouter session opens an interactive chat, and biorouter run -t "Summarize ./notes.md" sends one request and exits.

    Where your data lives

    Biorouter keeps its settings and chats as files on your computer. The app and the command line share them. On macOS and Linux:

    • Settings. config.yaml in ~/.config/biorouter/
    • Chats. sessions.db in ~/.local/share/biorouter/sessions/
    • Logs. ~/.local/state/biorouter/logs/

    On Windows they sit under %APPDATA%\Block\biorouter\. Run biorouter info to print the paths on your computer. Configuration lists every file.

    The desktop app

    The app is where you chat with a model, watch the agent work and read what it makes.

    The window

    The sidebar runs down the left. The rest of the window shows the page you opened. In a chat, tabs run across the top, the conversation fills the middle and the composer sits at the bottom.

    Files, figures and apps the agent makes open in a side panel on the right. In the conversation each one is a card; choose it to open it in the panel. In a live chat the panel opens on the newest one by itself. A terminal can open below the conversation.

    Drag the sidebar's edge to resize it, or press Cmd+B to hide and show it. Shortcuts on this page are shown for macOS; see Keyboard shortcuts.

    The sidebar

    From top to bottom:

    • Home. A greeting, a heatmap of your recent activity and a composer. Typing there starts a new chat.
    • New chat. An empty chat in a new tab.
    • Crew. Next release Your lab's shared workspace: channels, files and agent tasks. See Crew.
    • Components. A group holding the six rows below. It starts collapsed and stays the way you last left it.
      • Workflows. Saved recipes that start a chat with the same instructions, tools and model. See Workflows and scheduling.
      • Scheduler. Workflows set to run on a schedule, with each one's timing and last run.
      • Extensions. The tool servers the agent can use, each with an on and off switch, plus the BAAM marketplace and custom extensions. See Extensions and skills.
      • Skills. Instruction sets the agent loads when a task calls for one.
      • Knowledge. Knowledge bases the agent writes and reads. See Knowledge bases.
      • Built apps. Apps the agent built for you. This is the only place to delete one. See Built apps.
    • Recents. Your recent chats, grouped by day. A running chat shows an indicator. See all opens Chat history.
    • Settings. Pinned at the bottom. See Settings.

    Chat and the composer

    Type a request and press Enter. Shift+Enter starts a new line. Type / to pick a command, workflow, skill, knowledge base or extension, or @ to mention a file or folder. Paste or drag files and images onto the composer to attach them.

    The composer has three rows.

    • Above the text box. On the left, the working folder the agent reads and writes in. It is fixed once you send the first message. On the right, the extensions, skills and knowledge bases this chat uses, each with a count. Changes there apply to this chat only.
    • In the box. Your message, and Send, the arrow at the right. While the agent works and the box is empty, Send becomes Stop.
    • Below the text box. On the left, reasoning effort, which sets how long the model thinks before it answers, then the model this chat runs on (see Switching models). On the right, context shows how full the context window is. Its popover compacts the chat now, or sets when Biorouter compacts it on its own. Cost shows the estimated spend so far; turn it off in Settings → App → Appearance.

    In a narrow pane, reasoning effort, context and cost fold into one + button, Chat tools and settings. The model stays visible.

    While the agent works

    Each tool call is one line in the conversation; choose it to see the arguments and the result. Messages you send meanwhile wait in a queue. Add now, or Cmd+Enter, adds a message to the running turn without stopping it. Stop & send stops the turn and sends the message as a new one. The agent loop explains how a turn runs.

    Shell code blocks in a reply carry a Run button that sends the command to the terminal below the conversation.

    Working with messages

    • Copy is on every message.
    • Edit on your own message offers Edit in place, which changes it in this chat, or Diverge, which starts a new chat from the edited message.
    • Diverge on a reply opens a new window holding a new chat with the full history up to that point. The original stays as it was.
    • Select text in a reply, right click, and choose Ask about it or Quote it to put the passage in the composer as a quotation.

    Switching models

    1. Open the model chip Choose the model name under the text box, then Change model.
    2. Pick a provider and a model Then choose Select model. The next turn uses it; the conversation so far is unchanged.

    The change applies to this chat only. Tick Also use for new chats to make it the default too. Settings → Models → Switch models sets the model new chats start on, and existing chats keep their own. A private chat accepts only private models. See Private and public.

    Tabs and split panes

    Every chat is a tab. Open one with Cmd+T, close it with Cmd+W, and move between tabs with Ctrl+Tab and Ctrl+Shift+Tab. Drag a tab to reorder it. Opening a chat that is already open switches to its tab. Drag a tab out of the window to give it a window of its own, or onto another window's tabs to move it there.

    To split, drag a tab to the left, right, top or bottom edge of a pane. Dropping it in the middle of a pane moves it into that pane's tabs instead. A window holds up to six panes. Drag the line between two panes to resize them. Each pane has its own tabs, and each chat keeps its own model, folder and extensions, so you can watch several agents work at once.

    The terminal

    Choose the terminal icon at the top right of a chat (Open terminal) to open a terminal below the conversation. It starts in the chat's working folder. Each tab has its own terminal, and a hidden terminal's shell keeps running until you close its tab. + adds another terminal; Cmd+T does the same while the terminal has focus.

    History

    Chat history lists every chat, grouped by day. Open it with See all under Recents or with Cmd+2, and search it with Cmd+F. Choose a chat to reopen it in a tab.

    Each row can export or delete its chat, and a private chat's row offers Make this chat public, which asks you to confirm. Import chat brings in a chat someone exported. Show subagent runs adds the chats that subagents ran. Chats live in a local SQLite file; see Configuration.

    Settings

    Settings has three tabs.

    • Models. The current model, with Switch models and Configure providers. Local Model Inventory lists the local models you have and can download, and deletes ones you no longer need. Reset clears the selected provider and model.
    • Chat. Mode sets how much the agent does without asking: Autonomous, Manual, Smart or Chat only (see Security). Response styles picks Detailed or Concise answers. Capabilities sets the built-in abilities new chats start with. The tab also holds Memory, Contexts (skills that ship with Biorouter), App SDK, Editor and Project hints (.biorouterhints).
    • App. Configuration edits the settings file. Privacy holds the private and public protection, which is on by default. Workspace can stop agents from opening tabs on their own. Appearance covers notifications, the menu bar icon (and the Dock icon on macOS), prevent sleep and cost tracking. Palette, Mode and Font size set how the app looks. Usage appears while cost tracking is on. Then come Reset, Help & Feedback and Updates.

    Command line

    The biorouter command runs the same agent as the desktop app, from a terminal. It shares your settings, chats and extensions with the app.

    The desktop app includes the command; Getting started shows how to put it on your PATH. On a Linux server, install the biorouter-cli package instead. Add --help to any command to see its flags.

    Everyday use

    Choose a model

    Run biorouter configure once before anything else. The first time, it offers a local model (Llama Server), signing in with OpenRouter or Tetrate, or setting up a provider by hand. Run it again and choose Configure Providers to change the model, or Biorouter settings for the mode, tool permissions and turn limit. It needs a terminal, so a script uses models set instead and passes the provider's key in its environment variable, such as OPENAI_API_KEY.

    biorouter configure
biorouter models set --provider PROVIDER --model MODEL

    Chat in the terminal

    Run biorouter with no command to start a chat. On a real terminal it opens a full screen chat. Set BIOROUTER_CLI_CLASSIC to any value for the older line by line prompt, which Biorouter also uses when the output is not a terminal. When no settings exist yet, biorouter runs configure first.

    # A new chat, or a new chat with a name
biorouter
biorouter session -n gwas-followup

# Continue the last chat, or a named one with its history
biorouter session --resume
biorouter session --resume -n gwas-followup --history
    KeyIn the full screen chat
    EnterSend. While the agent is answering, the message waits and is sent when the turn ends.
    Shift+EnterNew line. Ctrl+J also works.
    Ctrl+CStop the running turn. With nothing running, clear the text; on an empty line, leave. Ctrl+D also leaves.
    UpRecall a message you sent earlier. Down goes back.
    PageUpScroll the conversation. PageDown scrolls back.
    /List commands, skills, extensions and knowledge bases. Tab or Enter picks one.

    Slash commands

    The desktop app, the full screen chat and the classic prompt share these commands.

    CommandWhat it does
    /compactSummarize the chat so far to free context.
    /clearClear the chat history.
    /effortHow hard the model thinks: quick, normal or deep.
    /goal/goal <condition> keeps working until it holds. /goal clear drops it.
    /loop/loop 5m <prompt> repeats a prompt. /loop stop <id> ends it.
    /schedule/schedule @daily <prompt> schedules a prompt. /schedule list shows the jobs.
    /ext:/ext:developer points the next reply at one extension, and /skill: and /kb: at a skill or a knowledge base. A name with spaces goes in parentheses: /skill(literature review).
    /<shortcut>Run a workflow you gave a slash shortcut.

    The terminal adds /rename <name>, /diverge [name] to copy the chat into a new one, /help and /exit. The classic prompt also has /mode auto|approve|smart_approve|chat, /plan and /endplan, /workflow [file.yaml] to save the chat as a workflow, /builtin and /extension to add extensions, /t for the color theme and /r for full tool output.

    Sessions

    Every chat is a session in one local store that the app and the command line share. The session commands come in two kinds.

    biorouter session list --limit 10
biorouter session export -n gwas-followup -o gwas-followup.md
biorouter session rename -n gwas-followup --new-name hla-loci
biorouter session remove --session-id 20260929_3

    The live commands need a biorouterd this terminal can reach, on BIOROUTER_PORT (3000 unless set) with the same BIOROUTER_SERVER__SECRET_KEY it was started with. The desktop app's own service picks a random port and a new key at every launch and publishes neither, so an open app does not count. Start a service you control:

    # Terminal 1: a service with a key you choose
BIOROUTER_SERVER__SECRET_KEY=KEY biorouterd agent

# Terminal 2: the same key
export BIOROUTER_SERVER__SECRET_KEY=KEY
biorouter session send 20260929_2 "Summarize your findings"
biorouter session watch 20260929_2 --follow
biorouter session attach 20260929_2
biorouter session cancel 20260929_2

    On a chat that is running, use attach, not session --resume: resuming opens a second agent on the same chat. send --no-wait returns at once, but the service stops a turn that nothing has been attached to for five minutes, so leave it off for long turns. A service started by hand has no user action key, so it refuses to steer a turn already running and says so; stopping still works.

    Run one task

    biorouter run sends one request and exits. Use it in scripts, on a cluster or in CI.

    biorouter run -t "Summarize the QC report in ./qc.html"
cat plan.md | biorouter run -i -
biorouter run --workflow variants.yaml --params gene=HLA-DRB1
biorouter run --workflow variants.yaml --explain

    For an unattended run, pin the model and set a limit, as below. The flags are under Reference, and the exit code says why a run stopped (Exit codes).

    biorouter run --no-session --provider llamacpp --model gemma4 \
  --output-format json --max-turns 10 \
  -t "Check samples.csv for duplicate sample IDs"

    Workflows and schedules

    A workflow is a saved recipe for a chat, and a schedule runs one on a cron expression. Workflows and scheduling explains how to write both.

    biorouter workflow validate variants.yaml
biorouter workflow install variants.yaml
biorouter workflow open variants -p gene=HLA-DRB1
biorouter workflow deeplink variants -p gene=HLA-DRB1

biorouter schedule add --schedule-id review-weekly \
  --cron "0 8 * * 1" --workflow-source ./review.yaml
biorouter schedule list
biorouter schedule run-now --schedule-id review-weekly
biorouter schedule sessions --schedule-id review-weekly -l 10
biorouter schedule remove --schedule-id review-weekly

    deeplink prints a link that opens the workflow in the desktop app. --cron takes five fields, six with seconds first, or @hourly, @daily, @weekly or @monthly; schedule cron-help prints examples. A job keeps its own copy of the workflow, so later edits to the file do not change it. --id is short for --schedule-id.

    Jobs run in the background while a Biorouter service is running. When this terminal can reach a running service (the same two variables as the live session commands), that service makes the change. Otherwise add and remove ask you to confirm and write the schedule file themselves, and a running Biorouter, the desktop app included, picks up the change within 60 seconds. run-now asks, then runs the job once in this terminal. Because a job is an agent that runs unattended, none of them goes ahead without a person at a terminal.

    Fix a missing tool

    biorouter doctor checks the tools extensions depend on (Git and uv are required; Python 3, Node.js, the AWS CLI, llama-server and Rust are optional), whether biorouter is on your PATH, the local model server, and whether a newer release exists. --fix opens a chat that already knows the failing tool and this machine, so the agent can repair it with you. With no tool named, it takes the first missing required one. --format json prints the checks for a script, and --no-update skips the release check.

    biorouter doctor
biorouter doctor --fix
biorouter doctor --fix uv

    Browser access

    biorouter serve shows the desktop app's interface in a web browser. Use it on a Linux server, in a container, or on a machine you reach over SSH. It starts its own biorouterd, which serves the interface and its API from one address.

    Set it up

    1. Install On a desktop computer, the app's command already includes serve. On a server, install the command line package. It puts biorouter and biorouterd in /usr/bin and the interface in /usr/share/biorouter/web. 
      # Debian, Ubuntu
sudo apt install ./biorouter-cli_*_amd64.deb

# Rocky, RHEL, Fedora
sudo dnf install ./biorouter-cli-*-1.x86_64.rpm
    2. Choose the model Run biorouter configure, as the account that will run serve. The browser cannot change the model later; see The model is fixed.

    The access token

    • The address ends in ?t= and a token. Unless you set a fixed one, the token is new on every launch and shown once.
    • Opening the address gives the browser a cookie and removes the token from the address bar.
    • The token is not used up. Anyone with the address can open it until serve stops, so stopping serve is how you revoke it.
    • To keep one address across restarts, set BIOROUTER_BROWSER_TOKEN to a long random value, for example from openssl rand -hex 32.

    Reach it from another machine

    For one person, keep the local address and forward the port over SSH, then open the printed address in a browser on your own computer.

    ssh -N -L 8765:127.0.0.1:8765 user@remote-host

    To serve other machines on the network, listen on every address. A token is then required, and serve prints a second address that other machines can use.

    biorouter serve --host 0.0.0.0

    Exposing the port exposes the agent. The browser can do what the desktop app does: run shell commands, read and write files, and spend your model credits, on the serving machine, as the account that started serve. There is one token and no user accounts, and the connection is plain HTTP. Beyond a trusted lab network, put a reverse proxy with TLS in front of it and limit who can reach the port.

    For a service that restarts on its own, keep the fixed token in an environment file that only the service account can read. The headless Linux guide has a systemd unit.

    The model is fixed

    A browser session cannot change its model or provider. This is deliberate. A chat that has used a private model may never reach a public one, and the desktop app can switch models only because it holds proof that a person asked. A browser tab cannot hold that proof.

    So the model is chosen once, at the terminal, and every chat in that serve runs on it: private for its whole life on a private model, public on a public one. A private chat started in the desktop app opens in the browser only when the host's model is private too. To change the model, stop serve, run biorouter configure and start it again.

    Private and public

    Every chat is private or public. Once a chat has used a private model or private data, Biorouter keeps it away from models hosted outside your institution.

    What is private

    A provider is private only when Biorouter can tell where inference runs. Ollama or Llama Server pointed at another machine is public. Azure OpenAI and Amazon Bedrock on the Public tab stay public even when they point at a UCSF address; only the Versa providers are treated as UCSF's. Models and providers lists every provider by tab.

    A private chat, model, extension or knowledge base shows a padlock and the word Private. Public ones show the word Public.

    How a chat becomes private

    A chat becomes private the first time either of these happens:

    1. A turn runs on a private model You send a message while Llama Server, Ollama or a Versa model is selected.
    2. A private data extension answers CDWAgent or UCSFOMOPAgent returns a result to one of the chat's tool calls.

    It then stays private. The mark survives restarts and travels with the chat into diverged chats, imports, scheduled runs and subagents. Only you can remove it; see Make a chat public.

    When you pick a private model for a public chat you have already sent a message in, Switch models says so before it applies: “After your next message this chat becomes private. Public models can't be used in it again unless you make it public from History.”

    What Biorouter refuses

    • A private chat cannot switch to a public model. In Switch models each public model reads “Unavailable: this is a private chat, so only private models may run in it. Make it public from History to use this one.” The command line and other chats get the same refusal, and it names the provider. To use a public model, start a new chat.
    • A public model cannot read a private chat, through chat recall or through the tools that read other conversations.
    • A public model cannot read a private knowledge base. The refusal names the base.
    • A public model cannot use a private extension, and one cannot be turned on in a chat that runs a public model.
    • A subagent never crosses the line. See the table below.
    • A private chat writing into a public one asks you first. Before the agent in a private chat sends a message to a public chat or changes its tools, Biorouter shows you what it will send. It asks once for each pair of chats.
    Parent chatSubagent's modelResult
    PublicPublicRuns. The subagent is public.
    PublicPrivateRefused.
    PrivatePrivateRuns. The subagent is private.
    PrivatePublicRefused. The task a private chat writes is private too.

    A public subagent is started without the parent's private extensions, and the parent is told what was left out. If a spawn is refused, retrying will not help: switch the parent chat, or start a new chat on the model you want.

    1. Open Chat history Choose See all under Recents, or press Cmd+2 (Ctrl+2 on Windows and Linux).
    2. Open the chat's menu Choose More actions (the three dots) on the chat's row, then Make this chat public. A chat opened from History also has a Make public button.

    biorouter session declassify SESSION_ID

    Turning the protection off

    Settings → App → Privacy has one switch, Privacy tiers, which is on by default. Turning it off asks you to type DISABLE PRIVACY TIERS, choose Turn off privacy tiers, then pass your computer's own password prompt. Turning it back on takes one click.

    While it is off, nothing separates private chats, extensions and knowledge bases from public models, and a chat that uses a private model or private data while it is off is not marked private. Turning it back on protects what was already marked, but it cannot mark what happened in between.

    The switch is kept in its own file beside config.yaml, not in it. An agent with a shell could still edit that file, which Biorouter cannot prevent, so it announces the off state instead: a note reading “Privacy tiers are off.” sits above every message box until you turn it back on. If the file was changed outside the app, the note says so.

    What this does not protect

    These rules govern what the agent can reach through Biorouter's own chats, knowledge bases and extensions. They prevent mistakes; they do not stop a determined person or an agent following injected instructions.

    • Files are not isolated. A public chat with a shell can read ordinary files on this computer, including files a private chat wrote and Biorouter's own chat store and knowledge base folders. The rules above cover what the agent reaches through Biorouter's tools, not through the shell.
    • The desktop is not isolated. Once you approve Biorouter Copilot for a request, the model receives screenshots and the text of other open apps. Close clinical windows first.

    Every model that is not private carries this line, on the model chip, above the API providers on the Public tab, and in biorouter configure, whether or not privacy tiers are on:

    “Not HIPAA-compliant, not on-premise, not local. This model can read files on this computer. Biorouter will not hand it another chat's transcript or a knowledge base marked private.”

    For patient data, use a local model or an institutional one, and check with your institution before you start.

    Security

    Where Biorouter keeps your credentials, which files it refuses to read, and how much the agent may do without asking.

    Credentials

    Provider API keys and other secrets go to your operating system's credential store, not to config.yaml. Biorouter reads the store once per process and keeps the values in memory, so one authorization covers the whole run.

    Credential storeWhat to expect
    macOS
    Keychain    		macOS asks for your password the first time a program reads the item. Choose Always Allow. The background service (biorouterd) and the command line (biorouter) are separate programs, so each asks once, and a program is never asked about an item it created. The grant survives updates.
    Windows
    Credential Manager    		No prompt. Windows protects the entries for your account.
    Linux
    Secret Service    		GNOME Keyring or KWallet. No prompt on a desktop session, which opens the store when you log in.

    Where no credential store answers, as on a Linux server, over SSH or in WSL, Biorouter keeps secrets in secrets.yaml beside config.yaml instead. Set the environment variable BIOROUTER_DISABLE_KEYRING to any value to choose that file on purpose. Prefer the credential store where there is one.

    • In the current release, on macOS and Linux the file gets your computer's default permissions, which can let other accounts on the computer read it. Run chmod 600 ~/.config/biorouter/secrets.yaml to make it readable by your account only. Biorouter keeps that setting when it writes the file again.
    • Next release Biorouter creates the file readable by your account only, and tightens an existing file the next time it writes it.

    Either way, anyone who can act as your account, or as root, can still read the file.

    An environment variable named after a key, such as OPENAI_API_KEY, always wins over the stored value.

    The secret guard

    A model with a shell can read any file you can. The secret guard refuses a tool call that reads or names a file whose purpose is to hold a credential. It works in every chat, in every permission mode and on every model, and it has no switch.

    It protects these names in any folder:

    KindNames
    Secret files.env, .env.*, secrets.* (Biorouter's own secrets.yaml included)
    Keys and certificatesSSH private keys such as id_rsa and id_ed25519, *.pem, *.p12, *.pfx
    Tool logins.aws/credentials, .codex/auth.json, .claude/.credentials.json
    More tool logins Next release.netrc, _netrc, .pgpass, .git-credentials, .docker/config.json, .kube/config, .config/gh/hosts.yml
    • Commands are read as the shell reads them. ~, variables, globs and cd are resolved before the path is judged, so cat ~/.aws/credentials and cd ~/.aws && head cred* are both refused.
    • A match is refused whether or not the file exists. A command that only names a protected file, such as echo X=1 > .env, is refused too.
    • Results are checked as well. When a credential still reaches a tool result, the guard replaces it with a marker such as [REDACTED:aws-secret-access-key] before any model sees it. It recognizes private key blocks, AWS keys, common provider tokens, and values under names such as *_API_KEY or *_TOKEN.

    To open one protected file on purpose, add a negation to .biorouterignore: the project's own file for paths inside the project, or ~/.config/biorouter/.biorouterignore for every path. For example, !**/.env.example in the project's file reopens its example env files. Any other pattern you add there keeps those files from the agent too.

    The guard stops mistakes, not a determined attacker. It cannot see a path a program builds while it runs, a recursive read of a parent folder such as grep -r key ~/.aws, or text inside a screenshot.

    Secrets for built apps

    A built app can hold its own secrets, apart from your provider keys. Its vault capability is off unless the app's manifest names each secret, for example "vault": { "encrypted": ["SPOKEAGENT_PASSCODE"] }. The values are stored encrypted in the app's .vault/ folder, and the app refers to each one by name as {{vault:NAME}}. Biorouter fills in the value when a tool runs, so the value never reaches the model. An exported app leaves .vault/ behind.

    Permission modes

    The permission mode sets how much the agent does without asking. Choose it in Settings → Chat → Mode, with /mode at the classic terminal prompt, or in the settings menu of biorouter configure. It is stored as BIOROUTER_MODE.

    ModeValueWhat the agent does
    AutonomousautoUses tools and edits, creates or deletes files without asking first. This is the default.
    ManualapproveAsks before every tool call, unless you chose Always Allow for that tool.
    Smartsmart_approveRuns calls with low risk and asks before the rest.
    Chat onlychatNo tools and no extensions. The model only answers.

    What asks in every mode

    A few actions ask even in Autonomous, and no hook can answer for you:

    • Writing or deleting under a protected system folder, your home folder itself, or a credential store such as ~/.ssh.
    • Reading, saving or deleting a global memory, which every chat on the computer shares.
    • Observing or controlling the desktop with Biorouter Copilot.

    An approval never reopens a call that was already refused, whether by your own Never allow, by a managed policy or by the block on destructive commands.

    Biorouter Copilot asks for each task

    Turning on Biorouter Copilot in Settings → Chat → Capabilities does not give it your desktop. Before its first capture or action for a request, Biorouter asks for approval that names the model and provider, where their data goes, and the computer to control. With a public model, the approval says that screenshots and application text can be sent to that provider. The approval covers that one request and ends when the reply finishes, when you stop it, or when the model changes. Chat only refuses every Copilot tool.

  allow:
    - "developer__text_editor"

    A tool name matches exactly or as an anchored regular expression. Deploy the file with your device management tools, such as Jamf, Ansible or Group Policy.

    • On macOS and Linux the file is read only if it and its folder belong to root or to you, and neither the group nor others can write to them. On Windows the %ProgramData% location is trusted, and ownership is not checked yet.
    • A file that fails the check or does not parse is ignored with a warning, and Biorouter runs as usual.
    • BIOROUTER_PATH_ROOT moves the file into <root>/managed/.

    Shell sandbox

    The shell sandbox is off by default. With the environment variable BIOROUTER_SHELL_SANDBOX set (it has no effect in config.yaml), each shell command runs in an operating system sandbox that lets it write only to the working folder and the temporary folder, and blocks outbound network where the kernel allows it. biorouter doctor shows which parts your computer gets. The sandbox is Seatbelt on macOS, and Landlock with seccomp on Linux, or bubblewrap where the kernel lacks them. Windows has no shell sandbox yet.

    • auto (or 1, true, on) uses the best sandbox available. Where there is none, it warns once and runs the command anyway.
    • strict refuses to run a command when a full sandbox is not available.
    • BIOROUTER_SHELL_SANDBOX_NETWORK=1 lets sandboxed commands reach the network.

    Apart from the sandbox, a block that is always on refuses a few commands that cannot be undone, such as rm -rf /, disk wipes and fork bombs, in every mode.

    Extensions and skills

    Extensions give the agent tools for a clinical database, a knowledge graph, Word and Excel files or a website; skills give it written methods for doing one kind of task the same way every time. Both install from BAAM, the Biorouter AI Agent Marketplace.

    What an extension is

    An extension is a server that speaks the Model Context Protocol (MCP), an open standard. It offers tools the agent can call, and it can also offer resources to read and prompts to start from. Any MCP server that runs as a command on this computer, or over streamable HTTP, can be added. The older SSE transport is not supported.

    Before it starts an extension through npx or uvx, Biorouter looks the package up in the OSV database of known malicious packages and refuses to start one that is listed.

    Skills

    A skill is a folder holding a SKILL.md file: a short header with a name and a description, then plain instructions. It adds a method rather than a tool, such as a quality control checklist, a lab's plotting style or the steps for using an API. The folder can also hold scripts and templates the agent reads when it uses the skill.

    ---
name: rnaseq-qc
description: RNA-seq quality checks.
---

1. Drop samples under 10M mapped reads.
2. Plot a PCA and flag outliers.
3. Report what was dropped and why.

    The agent reads each skill's description and loads the whole skill when a request matches it. To pick one yourself, type /skill: in the composer and choose it from the list. A skill is known by the name in its header, not by its folder's name.

    Install a skill

    • From BAAM. Choose Skills in the sidebar, then Browse skills. Tick the ones you want and choose the install button, which shows the count, such as Install 3 skills. BAAM publishes more than 120 skills in three groups: core, developer and biomedical.
    • From a repository or a .zip. Choose Skills → Add skill. Paste a repository URL and choose Look up, or drop a .zip.
    • Write your own. Choose Skills → Add custom skill, fill in the SKILL.md it opens, and save. It goes in Biorouter's skills folder.
    • From a terminal. Run biorouter skill install with a repository URL or the path to a .zip.

    The agent can install skills from BAAM or a URL as well. Each install or removal waits for you to approve it in the app; a reply in the chat cannot approve it.

    Packages

    A repository or a .zip can hold several skills that belong together. Biorouter reads the package's manifest when it has one and installs the skills as one package: a single row in every list, updated and removed as one. A package installs completely or not at all, and downloads come only over HTTPS from GitHub or biorouter.ucsf.edu.

    When a .zip holds loose skills and no manifest, Biorouter asks whether to install them as one bundle or separately. In a terminal, answer with a flag:

    • --as bundle installs them as one package.
    • --as individual installs each skill on its own.

    Turn skills on and off

    The skills button under the text box, Manage skills, turns a skill or a whole package on or off for this chat only. The switches on the Skills page, and biorouter skill enable or disable in a terminal, set the default for every chat. A choice made in a chat wins over the default.

    A few skills ship with Biorouter and are called Contexts: Word, PowerPoint, Excel and PDF documents, Knowledge, and a few about Biorouter itself. Turn them on or off in Settings → Chat → Contexts. They cannot be deleted, and the office ones load only for a matching task.

    Where skills live

    Biorouter reads skills from these folders, in this order. When two skills share a name, the one from the folder lower in the list wins.

    1. ~/.claude/skills/ holds skills shared with Claude Code.
    2. ~/.config/agents/skills/ holds skills shared with other AI agents.
    3. ~/.config/biorouter/skills/ holds the skills you install or write in Biorouter.
    4. ~/.config/biorouter/extensions/ holds the skills that come inside an installed extension, in its skills folder.
    5. .claude/skills/, .biorouter/skills/ and .agents/skills/ hold a project's own skills, in the folder where you run biorouter.

    Skills are plain text. A lab can share a skills folder to keep its analyses consistent without sharing any data.

    Workflows and scheduling

    A workflow is one file that starts a chat with the same instructions and tools, and optionally the same model, every time. Send it to a colleague to run on their own data, or let the scheduler run it for you.

    A workflow file

    A workflow is written in YAML (recommended) or JSON. It needs a title, a description, and instructions or a prompt (or both). Save this as review.yaml:

    version: "1.0.0"
title: Weekly cohort review
description: Counts new enrollments
instructions: Report counts, not records.
prompt: Summarize this week's enrollments.

    Running it starts a new chat with those instructions. The desktop app puts the prompt in the text box for you to send; the command line and the scheduler send it for you. Use .yaml rather than .yml: the command line reads only .yaml and .json.

    The fields

    FieldWhat it holds
    title, descriptionRequired. A short name and one line on what the workflow does.
    instructionsThe system instructions for the chat. A workflow needs instructions, prompt or both.
    promptThe first message.
    parametersValues filled in at launch and inserted with {{ key }}. See Parameters.
    extensionsThe extensions the chat needs. An env_keys list names the secrets an extension needs, and the command line asks for any that are missing.
    skillsSkills whose instructions are added before the first model call. A skill that is not installed, or is switched off in the chat, stops the run with an error. A bundle name adds every skill in the bundle.
    knowledge_basesvisible: the ids of the bases the chat may search. default: the base it writes to.
    settingsbiorouter_provider, biorouter_model and temperature, for this workflow only.
    activitiesButtons shown when the workflow opens in the desktop app. An entry that starts with message: is shown as a note above them.
    responseA json_schema the final answer must match. The validated JSON is printed as the last line of output.
    retrychecks run after the chat finishes (shell, file_exists, output_contains, json_schema), with max_retries and an optional on_failure command. A failed check starts the run again from the beginning.
    sub_workflowsOther workflow files this one can call as tools, each with a name, a path and fixed values. Experimental.
    authorcontact and metadata about who wrote it.
    versionThe file format version. Defaults to "1.0.0".

    The text fields are templates:

    • {{ workflow_dir }} is the folder that holds the file, so a workflow can point at files that travel with it.
    • {% extends "base.yaml" %} builds one workflow on another.

    The full reference is the workflow schema.

    Parameters

    Parameters make one workflow serve many studies. Each has a key, an input_type, a requirement and a description. Add these to review.yaml and replace its prompt:

    parameters:
  - key: study
    input_type: string
    requirement: optional
    default: MS-2041
    description: Study name
  - key: format
    input_type: select
    requirement: optional
    default: markdown
    options: [markdown, csv]
    description: Output format
prompt: Summarize enrollments in {{ study }} as {{ format }}.
    RequirementMeaning
    requiredMust be given at launch. Cannot have a default.
    optionalMust have a default.
    user_promptAsked for when no value is given.

    The input types are string (the default), number, boolean, date, select, which needs options, and file, which reads the file at the path given and inserts its contents. A file parameter cannot have a default. Every {{ key }} in the file must match a parameter, and every parameter must be used; Biorouter checks this when it loads the workflow.

    Save, run and share

    Save a chat as a workflow

    1. Open the chat summary In the chat you want to keep, choose the chat summary button in the chat header, then Make workflow.
    2. Read the draft Biorouter drafts the title, instructions and prompt from the conversation and fills in the chat's extensions, skills, knowledge bases and model. Edit what you need.
    3. Save Choose Create workflow. The workflow appears under Workflows in the sidebar.

    You can also ask in the chat, for example “Turn this chat into a workflow.” The agent shows you the workflow and asks you to approve it before anything is saved. Saved workflows live in ~/.config/biorouter/workflows/, where the app and the command line both find them.

    Run a workflow

    In Workflows, choose Use workflow, or Launch workflow, then Open in new window. The first time you run a workflow, Biorouter shows its title, description and instructions; choose Trust and execute to go on. If it has parameters, fill them in and choose Start workflow. Add slash command gives a workflow a shortcut you can type in any chat.

    biorouter run --workflow review.yaml --params study=MS-2107
biorouter workflow validate review.yaml    # check that it loads
biorouter workflow install review.yaml     # add it to the library
biorouter workflow list

    Share a workflow

    Send the file, or send a link. In Workflows, the Share workflow menu has Copy deeplink, Copy YAML and Export to file. The person who receives a file adds it with Import workflow, or runs it with the biorouter run command above. From a terminal, make a link that fills in parameters for them:

    biorouter workflow deeplink review.yaml --param study=MS-2107

    Opening the link opens Biorouter with the workflow loaded. A link encodes the workflow into a biorouter://workflow address, plus any parameter values you gave it. It does not carry files that sit next to the workflow, so send those with the file.

    Share the method, not the data

    A workflow carries instructions, not records. The file holds the steps, the parameters and the names of the extensions, skills, knowledge bases and model it needs. Biorouter leaves out API keys, memory and the conversation history; the file holds only the text you write or approve.

    • Each run is the recipient's own chat. It starts on their computer, with their extensions, their credentials and their models, under their institution's agreements. It follows the same privacy rules as any other chat: if it uses a private model or a private data extension, it becomes Private. See Private and public.
    • Data is read where it lives. A file parameter reads a file on the computer of the person running the workflow, when the run starts.
    • Results stay with the recipient. Nothing flows back to you. They share what they choose to share.
    • Edits do not travel back. A recipient's changes stay in their copy, and your file is unchanged.

    Read a workflow before you share it. It holds whatever text is in it. A draft made with Make workflow is written from the conversation, so remove any values that came from your data.

    Scheduling

    A schedule runs a workflow at set times with nobody watching. Each run is a new chat of its own, saved to history. Schedules run in the background while a Biorouter background service runs, such as the desktop app's or the one biorouter serve starts. They are kept in schedule.json in Biorouter's data folder, so they survive a restart, and every running service follows that file. A run that comes due while one of your chats is running a turn, or while the provider is limiting requests, is skipped and runs at its next time.

    The Scheduler page

    1. Open Scheduler Choose Scheduler in the sidebar, then New schedule. From Workflows, the clock button (Add schedule) does the same for one workflow.
    2. Fill in the schedule Give it a name, choose the workflow file, and set when it runs.
    3. Create it Choose Create schedule.

    Each schedule shows when it runs in words and how its last run went. From its row you can edit, pause, resume or delete it. Its page has Run now and lists every chat the schedule has run. Biorouter includes one schedule, Daily Meditation, which updates the Soul knowledge base from your recent chats at 3:00 each night; see Knowledge bases.

    From a chat: /schedule and /loop

    /schedule @daily Summarize new preprints on remyelination
/schedule "0 9 * * 1" Draft the weekly lab update
/loop 10m Check whether the alignment job has finished
    • /schedule <when> <prompt> runs a prompt until you remove it. When is an interval (5m, 2h, 1d), @hourly, @daily, @weekly, @monthly, or a cron expression in quotes. /schedule list shows them all. /schedule remove, run, pause, unpause and sessions take a schedule id.
    • /loop <interval> <prompt> is for short polling: 30s, 5m, 2h or 1d. A run that is still going when the next is due is skipped, and the loop stops itself after 100 runs. /loop lists loops, and /loop stop <id> or /loop stop all ends them.

    When the agent schedules something

    You can ask the agent, for example “Run the cohort review every Monday at 8am.” Every change the agent makes to a schedule shows an approval card first: creating one, running it now, pausing or resuming it, deleting it, or stopping a run. The card appears in every permission mode, Autonomous included. It says in words when the job will run, which workflow it runs and how, and the card for a new schedule shows the whole workflow. Only a person can approve it. Listing and reading schedules asks nothing.

    From the command line

    biorouter schedule add \
  --schedule-id review-weekly \
  --cron "0 8 * * 1" \
  --workflow-source ./review.yaml
biorouter schedule list
biorouter schedule run-now --schedule-id review-weekly
biorouter schedule sessions --schedule-id review-weekly
biorouter schedule remove --schedule-id review-weekly
biorouter schedule cron-help    # cron examples

    --cron takes five fields (minute, hour, day of month, month, day of week), or six with seconds first, in this computer's local time; "0 8 * * 1" is every Monday at 8:00. The schedule keeps its own copy of the workflow as it was when you added it.

    When this terminal cannot reach a Biorouter service, which is always the case next to the desktop app and in an agent's shell, the command writes the schedule file itself, and a running service picks it up within 60 seconds. In that case add, remove and run-now ask you to confirm at the terminal, and refuse when there is no terminal to ask, so an agent's shell cannot add a schedule on its own. When BIOROUTER_SERVER__SECRET_KEY and BIOROUTER_PORT point at a running service, that service makes the change without asking, or refuses it when the schedule would run on a private model.

    What a scheduled run needs

    • A prompt, since nobody is there to type the first message.
    • A value for every parameter without asking: use optional parameters with defaults, and no user_prompt ones.
    • The model's credentials, the extensions and the files the workflow uses, all in place on this computer when the run starts. A workflow that works in a chat can still fail on a schedule if it depends on something only you supply there.

    A failed run is recorded on the schedule, and the schedule runs again at its next time.

    Knowledge bases

    A knowledge base is a folder of linked pages that the agent writes from your papers, files, links and notes.

    What a knowledge base is

    Each base is one folder with its own git history, at ~/.config/biorouter/knowledge/<id>/. The sources you add and the pages the agent writes are kept apart, so a page can always be traced to the file it came from.

    PathWhat it holds
    raw/<source>/Each source as you added it, its Markdown conversion (source.md) and meta.yaml: title, link, checksum and credibility grade.
    knowledge/<type>/The pages the agent writes, one per concept, filed by type. Each page starts with a short YAML header that names its type.
    index.md, log.mdA catalog of the pages and a change log, both kept by the agent.
    schema.mdHow this base is written. The agent reads it on every run, and you can edit it.

    A base stays on your disk. Its only network calls are credibility lookups (Crossref and OpenAlex), the links you ask it to fetch, and the model that digests your sources. Git is built in; you do not need it installed.

    Create a base

    1. Open Knowledge Open the sidebar's Components group and choose Knowledge.
    2. Start a new base Choose the base's name at the top of the view. In the menu that opens, choose Create knowledge base…
    3. Name it and pick a format The format decides how pages are written and checked. Then choose Create knowledge base.
    ChoiceFormatUse it for
    General knowledgeOKFNotes, project context and anything that is not curated biology. Any page type and any link name; nothing is rejected.
    Curated biomedicalBioOKFBiomedical literature, or a base another institution will read. The vocabulary is checked, and every link names its evidence.

    The format is fixed when the base is created. The dialog says so: “You cannot change a knowledge base's format yet.” A base from an older version keeps working and is marked Legacy. biorouter knowledge create makes an OKF base; to make a BioOKF base, use the app or ask the agent.

    The BioOKF vocabulary

    BioOKF v0.5 is a strict biomedical profile of the Open Knowledge Format (OKF v0.2). A page's type is one of 28: 20 biomedical entity types, such as Gene, Variant, Disease and CellType, and 8 provenance and context types, such as Publication, Study and Dataset. A typed link uses one of 35 predicates: 24 positive predicates such as causes and treats, and 11 negations such as not_treats. Every link names its evidence: a knowledge level, an agent type and a primary source page. A value outside the vocabulary is flagged with the closest legal one.

    Visible bases and the primary

    Every base is visible to a chat unless you hide it. When the agent searches without naming a base, it searches all the visible bases and says which base each result came from.

    One visible base is the primary: where the agent writes when no base is named, the base it reads by default, and the base the Knowledge view shows. Soul is the primary until you choose another.

    • Hide a base from a chat. Choose the knowledge chip under the text box. Each base has a switch, and Hide all or Show all sets them together. A hidden base stays on disk.
    • Change the primary. In the Knowledge view, choose the base's name at the top and pick another base. Manage bases… lists every base with its format, its privacy and a switch that includes it in the chat.
    • Point one message at a base. Type / in the composer and pick it, or write /kb:ID.

    If you hide the primary, the next visible base takes its place. If you delete it, the chat has no primary until you choose one, and a write that names no base is refused with the list of bases to choose from.

    Add sources

    Open a base in the Knowledge view. Sources sit beside the graph; in a narrow window they are the Sources tab.

    1. Stage sources Drop files or folders on the dropzone, or choose it to browse. Folders and archives are unpacked, and each readable file is staged on its own. Paste text takes notes or an excerpt, and offers any links in it as sources of their own.
    2. Check the model The panel shows the model this base digests with. Change it there.
    3. Choose Digest staged sources Progress streams in as pages are written. Stop ends the run.

    Readable formats: PDF, Word (.docx), PowerPoint (.pptx, speaker notes included), Excel and OpenDocument spreadsheets (.xlsx, .xls, .ods), CSV, HTML, Markdown and plain text. Save an old .ppt as .pptx first. A scanned PDF with no text layer ingests with a warning.

    In a chat, ask the agent to add files, folders or links to a base. It runs the same pipeline and reports any source it could not digest. It can also digest past chats into a base.

    Conversion runs once. It also grades the source's credibility, and its result is kept. The digest is a subagent that works from that Markdown, never the original file. It reads the base's schema.md and the pages it may change, writes a page for the source, updates related pages and links them. If it fails, its changes are rolled back and the raw source is kept so you can try again.

    The graph

    The Graph draws each page as a node and each link as an edge. Choose a node to inspect its page. Type is the fill, credibility is the ring.

    • Fill. In a BioOKF base each of the 28 types has its own color, grouped into seven families: genomic, molecular, anatomy, clinical, exposome, physical and provenance. Provenance types are drawn as open circles, so the evidence stands apart from the science. In an OKF base the color comes from the type's name.
    • Ring. A source's ring counts its credibility in arcs, from four for peer reviewed to one for gray literature. Web and personal sources have a dashed ring and a retracted source a solid one. The legend groups them as Well sourced, Weakly sourced, Not academic and Retracted.

    Biorouter grades each source when it is converted. It looks for a DOI and checks it with Crossref, then OpenAlex, then checks the host, then looks for journal markers in the text. When none of these answers, the model grades it.

    TierRingHow it is detected
    Peer reviewed4 arcsA DOI resolves to a journal article, or the text carries clear journal markers.
    Book3 arcsCrossref or OpenAlex report a book or a chapter.
    Preprint2 arcsA preprint server such as arXiv, bioRxiv or medRxiv, or a DOI registered as a preprint.
    Gray literature1 arc.gov and .edu hosts, WHO, CDC, NIH, FDA, ClinicalTrials.gov, EMA and standards bodies.
    WebDashedAny other page.
    PersonalDashedPasted text with no stated source.
    RetractedSolidCrossref or OpenAlex mark it retracted, whatever its tier.

    A graph with nodes and no edges means the pages hold no links, and a lint reports each of them as an orphan.

    Search, history and restore

    • Search. The agent searches the pages by keyword (BM25), and the original source text when you ask for it. In a chat it reads the pages it finds and answers from them.
    • History. Every change is a git commit tagged by kind: ingest, link, flag, query, lint, restore or manual. Change log, in the base's ⋯ menu, lists them, and log.md keeps the same record.
    • Restore. In the change log, Preview shows the base as it was at a commit, and Restore adds a new commit that returns the base to that point, so a restore can itself be undone.

    Export and import

    Export as .brkb, in the base's ⋯ menu, writes the whole base to one file: pages, original sources and git history. To bring one in, open Manage bases… and choose Import from .brkb. The import keeps its id, or takes a numbered suffix if that id is in use, so it never replaces a base you have. A private base stays private when it is exported and imported. A .brkb dropped on the dropzone is not imported.

    Merge two bases

    Ask the agent to merge one base into another. It previews the merge first: what carries over, what is renamed and what the result's privacy will be. Then it merges.

    • The destination wins every clash. An incoming page whose identifier already exists is renamed, and every link to it is rewritten.
    • Sources the destination already holds are skipped. The source base is left unchanged.
    • The merge is one commit, and any failure leaves the destination as it was.
    • A BioOKF base can merge into an OKF base. An OKF base cannot merge into a BioOKF base.
    • The result takes the more sensitive privacy of the two.

    Ingest, query and lint

    Three operations run on a base. When one needs a model, it runs as a subagent with a limit on steps and time: 60 steps and 15 minutes to ingest a source, and 30 steps and five minutes to answer a query or repair what a lint found.

    OperationWhat it does
    IngestDigests one source into linked pages, as one commit. Run it with Digest staged sources, from a chat, or with knowledge ingest.
    QuerySearches the base and writes an answer that cites its pages. knowledge query --save also files the answer as a page.
    LintReads every page and reports orphans, contradictions, missing pages, stale sources and anything that breaks the format's rules. In a BioOKF base that includes the vocabulary, the evidence on each link, and sources that are retracted or too weak for the claims on them. Check for problems and a chat only report; knowledge lint --fix lets the agent repair what it finds.

    Soul

    Soul (id soul) ships with Biorouter and starts empty. It collects lasting facts about you: how you approach research questions, the tools and commands you use, and the name, role and preferences you mention.

    A schedule named Daily Meditation keeps it current. Every day at 3:00 AM, while Biorouter's background service is running, it runs the Meditation workflow, which uses the update-soul skill to read up to three recent chats and add what matters.     Built apps

    Agent Drafter builds apps: a small web page with its own agent, which fills panels, draws charts and asks you questions while you use it.

    What an app is

    An app is a TypeScript front end (index.html and src/main.ts) with a manifest.json that sets its agent: instructions, model, extensions, skills, knowledge bases and what the app may do. Apps live in ~/.config/biorouter/agent_drafter/<id>/. Biorouter's background service serves each one at /apps/<id>/ and connects the page to its agent over a WebSocket.

    Build one when a task needs a working surface rather than a transcript: a cohort reviewer, a variant workbench, a knowledge graph explorer, a dashboard for one lab. To see every app you have, open the sidebar's Components group and choose Built apps.

    How the agent drives the app

    Each app's agent gets a set of tools that act on the page. A call becomes a message on the app's socket and the page's SDK applies it. What you do in the page, such as answering a form or selecting a row, comes back over the same socket.

    ToolWhat it does
    ui_describeLists the page's regions, panels, declared actions and signals, and state. The agent calls it first.
    ui_panel, ui_renderOpen a panel, or render widgets (cards, tables, stats, forms, Markdown) into a target.
    ui_patchChange rendered widgets in place by id, keeping scroll position and typed input.
    ui_chart, ui_graph, ui_figureDraw a chart, a network graph, or an Auto Visualiser figure such as a volcano plot or a survival curve.
    ui_htmlRender HTML that Biorouter has cleaned of scripts and forms. Off unless the app allows it.
    ui_highlight, ui_notify, ui_suggestPoint at a region, show a short message, or offer up to five next steps the user can choose or ignore.
    ui_theme, ui_layoutSwitch the theme pack, accent, light or dark mode and density, or rearrange the layout.
    ui_state, ui_patch_stateRead and change the shared state the page is bound to.
    ui_askShow a form and wait for the answer. See Questions that wait.
    ui_subscribeListen to signals the app declares, such as a row being selected.
    app_call, emit_resultCall an action the app registered, or return a structured result the app is waiting for.
    consultAsk one of the app's worker profiles a question that stands on its own. Works only when the app declares worker profiles; otherwise it says there are none.

    Regions

    An app marks the places the agent may write with a region attribute:

    <section data-br-region="results">
</section>

    The agent finds regions with ui_describe and writes to @region:results. It can also target @panel:ID, @main, @chat or a CSS selector such as #out. Panels need no region: every app has a dock for them. Up to 12 panels stay open by default, and the oldest closes when a new one opens.

    Questions that wait

    ui_ask shows a form in the page and holds the tool call until you submit it. The answers come back as the tool's result, so the agent can act on them in the same turn. Many apps have no chat box, so the agent asks this way rather than in prose.

    A form holds up to 24 fields and waits up to 300 seconds by default. If the page closes or reconnects, the waiting question is released. Unlike ui_ask, ui_suggest never makes the turn wait.

    Exporting

    Export to a folder offers two modes:

    • Launcher (app + scripts) writes the app and its launch scripts. It uses the knowledge bases, skills, extensions and models already on the computer that runs it.
    • Full (bundle server-side content) also packs the app's knowledge base (as a .brkb file) and the skills you tick, and optionally biorouterd itself. BAAM extensions you tick are listed in export.json, at the top of the folder, for the recipient to install. On the first run the launcher lists the skills and knowledge base and asks first. If you agree, it installs the skills and copies the knowledge base to ~/.config/biorouter/knowledge-imports/, for you to bring in with Import from .brkb in Knowledge.

    The folder runs without a build step or Node.js. On macOS open run.command, on Linux run bash run.sh, and on Windows open run.bat. The launcher uses the biorouterd bundled in a Full export, or the one Biorouter installed on the computer. If there is none, it stops and says so; install Biorouter, or set BIOROUTERD_BIN to its path. It starts biorouterd in the background when it needs to and opens the app in the browser. An export carries no API keys, so the app uses the models configured by whoever runs it. The app's vault is never exported.

    Security model

    Biorouter treats an app's page as untrusted.

    • The socket. Each app has its own socket token, held in memory for one run of the background service and never written to disk. The socket accepts only the app page's own origin.
    • What the page sends. Action arguments, signals and widget submissions reach the agent wrapped in <app-data>, which the agent is told to treat as data, not instructions.
    • What the agent writes. State bindings set text and a short list of attributes, never code. ui_html is off unless the app allows it, and Biorouter cleans the HTML even then.
    • Capabilities. Control of the page is on by default, since it reaches only the app's own page. Files, data sources, compute and the vault are off until the manifest grants them. A signal that starts a turn by itself is off, and only you can turn it on; the agent cannot.
    • Knowledge. An app reads only the knowledge bases its manifest names, and writes only where it is granted write access.
    • Sensitive data. An app with an OMOP or CDW source, or a knowledge base it can write, may not send work to a public model. A model route or a worker profile that names one is refused.

    An app's agent is a chat like any other, so the rules in Private and public apply to it.

    Crew

    Crew is where a lab works together in the Biorouter desktop app: channels, shared files, and agent tasks the whole channel can see. One member, the host, runs the workspace on a shared Linux server.

    Crew arrives in the next release. It is merged into Biorouter's main branch but is not in a published release yet, so the app you download today does not have it.

    The examples use the workspace chen-lab on the server lab.example.edu, hosted by Alice Chen (@alice), and the member Bob Lee (@bob). A word in braces, such as {team}, is a name Crew fills in. Every dialog, message and command is in the Crew manual on GitHub.

    What Crew is

    • Open it from Crew in the sidebar, below New chat.
    • A workspace holds teams, and a team holds channels. You see only the channels you are in. There are no direct messages.
    • Only the host invites people, lets them in and removes them. A channel owner, at first its creator, manages each channel.
    • Privacy is Private or Public. It decides which AI models may read the workspace, not which people see it. Each channel is labeled "Restricted" or "Public-safe". Only a local model or one approved for the workspace's institution may read a Restricted channel.
    • The desktop app and the biorouter crew commands share one background service on your computer, so both show the same workspaces.

    What you need

    • The desktop app. Tested on macOS. Crew does not work in a web browser opened with biorouter serve, which shows "Crew needs the Biorouter desktop app" in its place.
    • A server account. Your own login on the lab's Linux server, with an SSH key, a password or a verification code. Your IT team provides it.
    • Crew on the server. The program biorouter-crew, installed in ~/.local/bin of every account that connects, the host's included. You install it yourself, or IT does.
    • A verified server. The server's SSH host key in your known hosts file. Crew never accepts a new server by itself, so check the fingerprint with IT once.
    • An invitation. The host sends it. It expires after 24 hours.

    The approval secret

    On macOS and Linux, the background service acts for you only with your approval secret. It is not your login or SSH password. The first time the service starts, and after each restart of your computer, Biorouter asks you to choose one.

    1. Set it In "Set approval secret for shared Biorouter daemon", enter 32 to 4096 letters, numbers and punctuation marks, with no spaces. You can paste it.
    2. Keep it Save it in your password manager. Biorouter cannot show it again.
    3. Confirm it Enter it again in "Confirm shared daemon approval secret". Biorouter opens.

    Quitting the app leaves the service running. When you open Biorouter again, type the secret in "Connect to existing Biorouter daemon". If you forget it, restart your computer and set a new one. Windows has no approval secret. There, quitting the app stops the service, and the biorouter crew commands do not work.

    The agent loop

    Each request runs as a loop of model calls and tool calls. Biorouter runs the loop, so it decides what the model sees and what may run.

    How a turn runs

    StageWhat happens
    ReceiveOne turn runs in a chat at a time. A message you send while it runs waits in a queue; see Steering a running turn. Commands such as /goal and /schedule are handled before the model is called.
    Build contextThe system instructions (base instructions, permission mode, date, guidance from each extension, any workflow instructions), the tool list, the skills in use, up to five passages from a knowledge base you referenced with /kb:, a map of the working folder of up to about 2,000 tokens, and the conversation so far. At 80% of the model's context window, older turns are summarized for the model; your history is kept in full.
    Call the modelThe reply streams back as text, tool calls, token counts and a reason for stopping. A reply cut off at the length limit is continued up to 12 times.
    Permission gateEach tool call is checked by the administrator's managed policy, the command policy, your permission mode and any hooks. Deny is checked before ask, and ask before allow; an administrator's deny or ask always wins. A few destructive commands are refused in every mode. The modes are on the Security page. Up to 8 tool calls run at once; writes to the same file run one at a time.
    Run and returnThe result goes back to the model. A large result is saved to a file, and the model gets a preview. Private keys and stored credentials in a result are withheld. An error goes back as an error the model can act on, not as the end of the turn.
    FinishWhen the model answers without a tool call, the active checks run: a workflow's response schema, Stop hooks and a /goal. A failed check sends the turn back to work. A Stop hook can do this 5 times, and a /goal is dropped at the limits in Goals. A workflow's retry checks run after the chat finishes, and a failure starts the run again from the beginning. The whole turn is saved to the chat.

    Loop limits

    Several checks watch a long turn for repetition and runaway cost. Most warn the model first.

    • Exact repeats. The same call with the same arguments: a warning at 3, and the fifth identical call is refused.
    • Near repeats. Nearly the same call, or two calls taking turns: a warning at 4.
    • Repeated failure. The same failure from the same tool: a nudge at 3, then “change approach or ask the user” at 5. After 6, the next call to that tool is refused.
    • Failures in a row. Failed calls to any tool: a nudge at 3. At 6, the model is told to change route or hand the work back to you.
    • Stalls. A check for a stall after 30 actions in one turn, then every 10. A confirmed stall gets a short grace period to answer, then the turn stops.
    • Work without your input. The turn stops at 100 turns or 200 tool calls and names the limit. Quick reasoning effort halves both, and Deep doubles them. Set BIOROUTER_MAX_TURNS or BIOROUTER_MAX_TOOL_CALLS to change them; the command line also takes a turn limit for one run (see Command line). A message you add to the turn resets both counts.
    • Reply budget. A limit on the time, tokens or cost of one reply. Off by default. Set BIOROUTER_REPLY_BUDGET_SECONDS, BIOROUTER_REPLY_BUDGET_TOKENS or BIOROUTER_REPLY_BUDGET_USD for a warning, a request to wrap up, then a stop.

    Delegation and several chats

    Subagents

    Ask in plain language, for example “Have a subagent check the QC report while you draft the methods.” A subagent is a separate chat that runs one task and reports back to the chat that started it. Several can run one after another or in parallel. In the desktop app each one opens in a background tab marked as a subagent, where you can read it as it works, type to steer it, and stop it. Closing the tab does not stop it. If you typed into it, the parent is told.

    • A subagent has the parent's extensions unless you name fewer, 25 turns (BIOROUTER_SUBAGENT_MAX_TURNS) and 5 minutes by default.
    • It cannot start subagents of its own, change the parent's extensions, or change schedules.
    • It never moves work across the privacy boundary. A public chat cannot start a subagent on a private model, and a private chat cannot start one on a public model. A public subagent is given no private data extensions, and the parent is told which were left out. See Private and public.

    The subagent tool is offered only when all five of these hold. If a request for a subagent gets an ordinary answer, check them in order.

    1. The permission mode is Autonomous (the default).
    2. The model's name does not start with gemini.
    3. The chat is not itself a subagent.
    4. At least one extension besides Workspace Control is turned on.
    5. The chat is not a built app that delegates to its own worker profiles.

    Workspace Control

    Workspace Control lets the agent work across your chats. It is on by default. To turn it off for new chats, use Settings → Chat → Capabilities in the app, or run biorouter configure in a terminal and choose Toggle Extensions, then workspace. The agent can:

    • open a new chat in a tab, a split pane or a new window. New tabs open in the background and start in your working folder.
    • list what is running, and read another chat as a summary, a transcript, its tool calls or a subagent's starting instructions. A public chat cannot read a private one.
    • send a prompt into another chat and wait for it to finish.
    • change another chat's extensions, skills, model or knowledge bases.

    Some changes show a confirmation card in every permission mode: giving a chat an extension that can start programs, removing one that matters for security, switching its model provider, or adding a skill. The changed chat shows who changed what. The first time a private chat writes into a public chat, Biorouter shows you what it would send and asks first.

    From a terminal:

    # chats, with their subagents

# follow a running chat

    attach needs a biorouterd this terminal can reach, and the desktop app's own service is not one. Command line covers the session commands.

    Steering a running turn

    You do not have to wait for a turn to finish. A message you send while it runs waits in a queue at the text box, with two choices:

    • Add now adds the message to the running turn without stopping it. With the text box empty, Cmd+Enter (Ctrl+Enter on Windows and Linux) does the same for the first message in the queue.
    • Stop & send stops the turn and sends the message as a new one.

    An added message reaches the model at the next safe point. A running tool is never cut off for it. If an approval card is waiting, the message waits until you answer the card, because a message never answers a card. If the turn ends before the model reads it, the message stays in the chat marked as not answered. A message with attachments cannot be added to a running turn; it waits, or you can use Stop & send.

    A browser opened with biorouter serve cannot add messages to a running turn, and neither can any other client of that service. Stop still works. Use the desktop app. biorouter session attach can add to a running turn only on a service started with a user action key; see Command line.

    Goals: /goal

    /goal keeps the agent working until a condition you can check is true.

    /goal the notebook runs with no errors

    Work starts at once. Each time the agent tries to finish, an evaluator reads the recent part of the chat and checks the condition. If it is not met, the evaluator's feedback goes back to the agent and the turn continues. After 20 evaluations, or when the evaluator gives nearly the same feedback 3 times in a row, the goal is dropped and the agent reports what it did, what is unfinished and what stands in the way.

    /goal on its own shows the active goal, and /goal clear removes it. The goal is saved with the chat, so it survives a restart. Write the condition as an end state the agent can show, such as a file that exists or a test that passes.

    Configuration

    Biorouter keeps its settings in one YAML file that the app and the command line share. This page lists the files Biorouter writes, the environment variables it reads, and which source wins.

    The settings file

    ~/.config/biorouter/config.yaml holds the provider and model, the permission mode, turn limits, the extensions under the extensions key, and the other general settings. The app writes it when you change Settings, biorouter configure writes it from a terminal, and you can edit it by hand.

    BIOROUTER_PROVIDER: llamacpp
BIOROUTER_MODEL: gemma4
BIOROUTER_MODE: smart_approve
BIOROUTER_MAX_TURNS: 100

    Credentials are kept elsewhere; see Security. biorouter info -v prints the values stored in config.yaml.

    Where files live

    The paths below are for macOS and Linux. On Windows, ~/.config/biorouter/ is %APPDATA%\Block\biorouter\config\, and both ~/.local/share/biorouter/ and ~/.local/state/biorouter/ are %APPDATA%\Block\biorouter\data\. biorouter info prints the paths on your computer.

    Which setting wins

    When the same setting comes from several places, the first of these wins:

    1. Managed policy, for the tool permissions and hooks it names.
    2. Environment variables, for the program that starts with them.
    3. config.yaml.
    4. Defaults.

    For example, BIOROUTER_MODE=chat biorouter starts a terminal chat in Chat only mode and leaves the file alone. Most settings in config.yaml, such as those in the first table under Environment variables, can also be set as a variable of the same name. The variables in the second table work only from the environment.

    When a change takes effect

    • config.yaml is checked each time a setting is read, so a change from the app, biorouter configure or an editor is seen at the next read, without a restart.
    • A chat takes its permission mode and the managed policy when its agent starts. Open a new chat to be sure a change applies.
    • Environment variables are read by each program when it starts. A command sees your shell's variables. The desktop app passes the environment it was opened from to its background service, so an app opened from the Dock or the Start menu does not see a variable set only in a terminal.
    • Secrets are read from the credential store once per process. A key saved in the app is used at once. A key changed by another program is read when Biorouter's background service next starts.
    • Next release On macOS and Linux the background service keeps running after you quit the app, until the computer restarts. It keeps the environment and the secrets it started with, so a variable or a key changed by another program reaches it only once the service restarts. See The background service.

    Architecture

    Biorouter has three layers: the interface you use, the agent that reasons and acts, and the extensions that give it tools. In the desktop app and the browser, the agent runs inside a background service, biorouterd.

    Three layers

    • Interface. The desktop app, a browser opened with biorouter serve, or the biorouter command line. It shows the conversation and holds no reasoning of its own.
    • Agent. The loop that sends the conversation to a model, runs the tools the model asks for and returns the answer, together with chat history, the connections to model providers, and the running of workflows and schedules. See The agent loop.
    • Extensions. Servers that speak the Model Context Protocol (MCP), the open standard for giving a model tools. An extension that ships with Biorouter and one you install look the same to the agent. See Extensions and skills.

    The background service

    biorouterd serves the agent over local HTTP and WebSocket. The desktop app starts one for all of its windows. Schedules run inside it, so they run while it runs.

    In the current release the service stops when you quit the app. From the next release, on macOS and Linux it keeps running after you quit, until the computer restarts; see Crew. On Windows it still stops when you quit.

    The same release adds Crew, which connects the service to a lab workspace. The host runs the workspace with biorouter-crew on a shared Linux server, and each member's service reaches it over SSH through that member's own account on the server. Each member's agent still runs on their own computer, with their own model.

    How each interface connects

    InterfaceHow it reaches the agent
    Desktop appThe app's main process starts biorouterd, and each window talks to it over HTTP and WebSocket, through a client generated from the service's OpenAPI description.
    Browserbiorouter serve starts biorouterd, which serves the same interface from its own address. See Browser access.
    Command line, on its ownBy default, biorouter session and biorouter run start the agent inside the terminal's own process. session list, export, rename and remove use the chat store directly. Nothing else needs to run.
    Command line, livesession send, watch, attach and cancel talk to a running biorouterd, because a turn in progress exists only inside the service running it. See Sessions.
    Command line, shared Next releaseWith --shared-daemon, biorouter session and biorouter run use the same background service as the desktop app, as biorouter crew does.

    The app and the command line share one settings file, one credential store and one chat store, so a provider, an extension or a chat set up in one appears in the other. See Where files live.
