# Crew UI fixture integrity and evidence correction

The initial Bob enrollment attempt is not a clean product regression. After saving a connection through the UI, the original tester manually changed its connection ID, device fingerprint, and public key to a separate pending prepared identity in the local fixture registry. That bypassed the normal save/receipt flow. The resulting combination of an existing connection, an unconsumed matching `pending_device`, and empty `completed_preparations` was not generated by the current successful prepared-identity save path.

A subsequent reviewer checked the visible public key and fingerprint, but those checks alone could not restore provenance for the manually altered record. The observed challenge failure must not be described as a demonstrated cryptographic defect or a successful ordinary enrollment test. The old profile is retained as contaminated test state; nominal acceptance must use a new Bob profile and complete save, invitation, and enrollment through the actual application. Each invitation must bind the public key displayed by that saved connection. An unused hosting-preparation key is not interchangeable with it.

The investigation did identify a separate UI issue: a periodic unauthorized workspace refresh could replace the actionable Join error. Action and refresh errors are now separate, successful refresh clears only the refresh error, Dismiss clears both, and SSH recovery help follows the visible error. The signer is also loaded and checked before issuing the short-lived broker challenge, so a desktop keystore interaction does not consume the challenge lifetime. Broker diagnostics distinguish device binding, enrollment-key binding and expiry without relaxing any predicate, signature check, one-use nonce, or timeout. These changes require their own fresh-binary validation.

Claims made before the clean-profile rerun that all three clients completed the workflow were unsupported. Alice's initial host setup and human post have UI/journal observations. The original Carol connection/enrollment was not established, and Bob's contaminated attempt cannot satisfy it. The acceptance ledger must record the replacement three-profile run and its exact binaries before upgrading those gates.

The replacement run subsequently completed clean Bob and Carol UI enrollment, three-person human chat, file upload/download with SHA-256 verification, and private-channel invitation/ownership checks. Three isolated GUI clients now run concurrently. Initial multi-instance launch failures came from the test process's restricted GUI sandbox and were resolved by the scoped GUI launch permission; they do not establish a platform incompatibility. Full agent, conversational MCP, provider-boundary and load acceptance remain separate gates.
