# BioRouter Crew: existing architecture and required security boundaries

> September 22 design update: [the implementation plan](implementation-plan.md) now follows the user's no-administrator, home-based deployment requirement, 2–50-user scope, cluster Public/Private toggle and built-in saved-SSH/MCP integration. It also contains the required three-user AWS/dev-app computer-use testing plan. Earlier deployment recommendations in this research snapshot are superseded; recorded source findings and probe results remain historical evidence, not rootless product acceptance.

Research date: 2026-09-21. Source baseline: `314f3b268c24663a8696dbbbd5aa76a171d0fab8`. This is source investigation and proposed architecture, not a claim that Crew is implemented or that existing deployments satisfy HIPAA requirements. No private records, real patient data, provider credentials, or production configuration contents were read for this investigation.

The [implementation plan](implementation-plan.md) is the authoritative consolidated design, including the more detailed SSH authentication and human-device enrollment contracts added after independent review. This document supplies the source investigation and architecture rationale.

## Main finding

BioRouter already supplies valuable building blocks: a Rust agent runtime, MCP extension dispatch, provider privacy classification, institutional affiliations, persisted sessions, live event streams, scoped tool approvals, ACP integration, and Electron UI infrastructure. Crew should reuse these through a **new collaboration control plane and per-user workers**, rather than exposing the existing single-user daemon to all SSH users.

Three existing assumptions are incompatible with a shared server without additional controls:

1. Session privacy is not user ownership. Current workspace authorization deliberately permits an agent to steer any local session it may read; unrelated sessions are permitted when the privacy tier allows them. Crew must separately enforce account, workspace, team, channel, and agent-owner permissions.
2. Current privacy protections have local opt-outs and locally writable state. Crew's server policy must be mandatory and cannot become weaker when a desktop preference changes.
3. The existing developer-shell sandbox restricts writes, not reads. A public-model worker that can read a user's entire home can obtain private data outside the chat API. Crew needs a read-isolated execution environment before permitting public workers to browse files on a private host.

## ACP and MCP are different parts of the design

ACP is an agent-client protocol: initialize, create/load an agent session, send a prompt, stream updates, request permission, cancel. It is a good adapter for invoking an owned agent and translating its progress into a channel timeline. It does not define teams, channel membership, durable message fan-out, attachment authorization, or the SSH account-to-principal binding. The official v1 transport page defines stdio and describes Streamable HTTP as a draft; custom bidirectional transports must preserve ACP lifecycle semantics. Use the version BioRouter actually supports and negotiate capabilities. [ACP overview](https://agentclientprotocol.com/protocol/v1/overview), [ACP transports](https://agentclientprotocol.com/protocol/v1/transports).

MCP exposes tools, resources and prompts to a host, with the host controlling context and security policy. It is appropriate for `crew.search`, `crew.read`, `crew.post`, attachment references and channel operations made by a user's agent. It should not become the durable chat replication protocol. The 2026-07-28 MCP architecture is stateless and differs from older stateful releases; protocol upgrades must be a deliberate compatibility task, not a side effect of Crew. [Current MCP architecture](https://modelcontextprotocol.io/specification/2026-07-28/architecture).

The checked lockfile contains `agent-client-protocol-schema 0.10.5` (`Cargo.lock:67–70`), `sacp 10.1.0` (`Cargo.lock:7222–7225`) and `rmcp 0.12.0` plus `0.14.0` (`Cargo.lock:6880–6905`). Lockfile versions alone are not a statement that every latest protocol feature is implemented.

BioRouter's ACP implementation is not a ready multi-tenant server:

- `BioRouterAcpAgent` stores a single `Arc<Agent>` and provider plus an in-memory session map (`crates/biorouter-acp/src/server.rs:37–65`). Configured extensions are loaded onto that shared agent (`:345–379`). Use a separate owned worker instance per execution compartment rather than one instance for the whole team.
- Stdio ACP loads the launching user's configured tools (`:1144–1154`). WebSocket ACP intentionally suppresses configured tools and client-registered stdio MCP (`:1270–1291`). Preserve that distinction; do not enable arbitrary process-spawning MCP registration merely to make Crew work.
- WebSocket ACP uses bearer-token and origin checks (`:1209–1254,1293–1323`). These are not multi-user ownership or channel authorization.
- ACP maps text/images and text resources, but audio and non-text embedded resources are currently ignored (`:396–430`). Crew attachments must remain durable downloadable objects even when a particular agent cannot consume that type; report unsupported agent input explicitly.
- ACP emits message, thought, tool and permission updates (`:436–625`). Crew should publish intentional user-facing progress, commands, tool status and shareable results; do not indiscriminately fan out raw provider frames, credentials, hidden reasoning or every local-session message.
- The permission bridge explicitly says ACP alone cannot distinguish a human click from auto-allow (`:618–625`). Sensitive Crew approvals need an authenticated owner-side UI action and a broker-verified request-bound approval.

## Proposed security model

### Identities and ownership

Use a stable server-assigned workspace ID, not a local SSH profile name. Profiles can point at the same remote deployment through different jumps, aliases and ports. Bind a remote principal to workspace ID plus the authenticated OS account's UID and an account-generation record; keep username as its stable visible label and nickname/avatar as mutable profile attributes. This avoids treating the same username on two hosts as one person and accounts for UID reuse.

On a single Linux host, an administrator-managed broker can authenticate a bridge process's Unix account through a protected Unix domain socket and kernel peer credentials. The bridge itself runs after normal OpenSSH login as the user. This account proof is not human-control authority: broker application admission additionally requires an enrolled device/session credential or a scoped worker grant, as defined in the implementation plan. Bare UID access cannot enroll a human key or mint a human grant. Never accept `$USER`, a request `username`, `X-Caller-Provider`, the UI avatar, or a client-supplied UID as identity proof. Every hop must preserve normal host-key verification, institution MFA and approved SSH configuration. If the broker is on another host, local Unix peer credentials do not automatically prove the remote user's identity: an additional trusted relay or approved mutually authenticated deployment is needed.

The broker owns collaboration records but does not execute shell commands as its service account. Each user's worker starts through that user's authenticated login and runs with that user's permitted OS identity, scheduler account and project allocation. A worker registration is bound to the kernel-authenticated principal plus an expiring, narrowly scoped agent grant. A client cannot register or prompt another user's agent by supplying their agent ID.

Core permissions:

| Operation | Required authority |
|---|---|
| Read channel/history/attachments | Active workspace identity, team membership, channel visibility, data compartment permission and applicable device/export policy |
| Post as a human | The authenticated human principal; account membership and channel write permission |
| Post as an agent | Worker grant bound to owner, agent, run, destination channel and accepted data labels |
| Prompt/steer/cancel an agent | Its owner; another member may request work conversationally but cannot trigger execution |
| Approve a sensitive tool action | Owner's authenticated interactive authority, bound to exact request/run/arguments; never a model-generated chat message |
| Create/invite/manage channel | Relevant team/channel permission; invitee must already have valid workspace identity |
| Remove a channel | Its original creator, as requested; admin quarantine and account-offboarding recovery are separate policy actions, never implicit ownership transfer |
| Change workspace privacy/provider policy | Institutional administrator/operator through a protected control plane |

Directory discovery should expose only users registered with Crew and permitted to be discoverable, not enumerate all system accounts. Presence is ephemeral and must not authorize any operation. Team membership does not authorize reading unrelated Unix files; sharing a file is an explicit copy or granted object, not a pointer that causes the broker to read arbitrary paths as itself.

### Mandatory policy intersection

For every read, retrieval, publish, provider invocation and tool result, compute an intersection of authenticated principal permissions, team/channel membership, object ACL, worker/run scope, data labels, approved model endpoint and workspace policy. An allow at one layer never overrides a deny at another. Client preferences may make this more restrictive, not less.

Treat channel visibility (`open-to-team`, `invite-only`) separately from data classification (`public-safe`, `restricted/PHI`). A team-open channel can still be restricted, and an invite-only channel can contain public-safe research. Add institution/project/dataset compartments and permitted processing destinations. An institutionally hosted provider is not a blanket clearance for another institution's dataset. Commercial hosting can be allowed for a particular restricted flow only when institution policy explicitly approves that exact deployment and use; do not infer approval from the provider brand or a boolean private flag.

The broker must verify workers against protected endpoint configuration and policy; ordinary workers cannot self-assert that a model is private. Private execution needs deny-by-default network egress with an approved provider proxy or narrowly approved destinations. Apply the same boundary to embeddings, OCR, transcription, summarization, title generation, telemetry, previews, external-link fetches, plugins and tool subprocesses—not just the main LLM request.

Public workers must not inherit private conversation state. Bind each run to owner, workspace, source channel, model policy and compartment. Reset or refuse incompatible model changes. A provider switch, membership change, policy change or revoked grant invalidates queued work and relevant long-lived streams. Check both at enqueue and immediately before execution/delivery.

The entire execution environment must support the claimed confidentiality boundary. A shell command can bypass application retrieval rules by reading files directly. Public workers therefore need explicit readable mounts, hidden host home/cache/SSH sockets, restricted process inspection, no arbitrary credentials, and a broker channel restricted to the worker grant. Separate user-owned processes without read isolation do not establish this. If the host cannot provide it, restrict public-model execution to public-only workspaces and keep protected cluster-file tools unavailable. Every worker, including a private-model worker, also needs isolation from human-control keys, unscoped sessions and enrollment/approval authority. If that separate boundary is unavailable, support human chat only; an approved private provider does not authorize its agent to approve its own actions.

The enforceable threat model must be stated: server-side controls protect against unauthorized peers, mistakes and compromised/scoped agents. An authorized human can still manually copy data they are entitled to read unless institutional endpoint controls also apply. Root administrators and host compromise are part of the trusted computing base, not solved by SSH encryption.

### Context retrieval and information flow

Default to the current channel's permitted conversation window and explicitly attached artifacts. Optional cross-channel retrieval can be convenient without sending every channel to every model: search only within the actor's approved channel set and data compartments, with filters applied before ranking, snippets, counts and pagination. Record which channel/message/file versions actually entered context. Cross-workspace retrieval is disabled by default and requires an explicit policy-compatible selection.

Derived context inherits the union of source restrictions. A summary, embedding, generated filename, image thumbnail or copied artifact is not automatically public. Publishing derived output requires that every recipient and destination satisfies that union. Preserve source-ACL dependencies and apply them to every future reader, including later invitees, search/replay and cached context; channel membership growth cannot silently widen the audience of retained derived material. Reading two separately restricted channels can produce output that neither whole channel may receive; offer the run's owner a restricted result and explain the missing destination permission.

Treat shared human and agent messages as untrusted task data. A colleague posting `@other-person-agent run ...` must not be interpreted as owner authorization. Only an authenticated owner action creates an invocation. Model-triggered slash commands still pass the same broker ACL, publication gate and request-bound approval rules.

Private-to-public movement should create a new release artifact with exact proposed text/files, source provenance, destination and an expiry. Institutional policy decides whether such release is even available. Approval releases only that artifact; it does not declassify the source channel or grant standing permission for subsequent messages. No automatic cross-workspace mirroring, automatic public summaries, or generic first-crossing grants for protected work.

### Storage and event boundaries

Keep the authoritative Crew store broker-owned, with one writer and an append-only JSONL journal as the canonical record. This follows the user's preference for simple portable text storage and streaming over throughput. Attachments are ordinary opaque files; derived search and lookup indexes can be rebuilt. Crew should not require SQLite, PostgreSQL, Redis or a container runtime to provide human collaboration. The existing worker's personal BioRouter session database stays separate from the shared channel journal.

Text files still need a transaction and recovery design. Use versioned records, monotonic sequence numbers, bounded frame lengths, record digests, a process lock, durable write/`fsync` ordering, and atomic manifest/checkpoint replacement on the same filesystem. A multi-event mutation must have one unambiguous commit boundary; replay ignores or quarantines incomplete trailing records and refuses corrupt committed history. Attachment finalization precedes the committed event referencing it, and orphan cleanup follows a recovery-safe grace period. Prefer one workspace journal initially to avoid pretending separate channel files give atomic cross-channel membership and invite changes. Segment and compact only with tested retention, audit and cursor semantics. Benchmark at expected team size before adding indexes or sharding.

Use local durable server storage for the writer and its live journal. An NFS home is not made safe merely by using JSONL: locking, cache visibility, atomic replacement and durability must be verified for that filesystem and cluster topology. Do not place independently writing brokers on several login nodes against the same journal. An administrator-provisioned persistent service host and local durable volume are the preferred baseline; approved storage support is a deployment prerequisite when unavailable.

Messages and events need immutable IDs, monotonically ordered per-channel positions, server timestamps, authorship, edit/tombstone events, idempotency keys, reply/thread relationships and ACL/policy revisions. Reconnect should resume from a durable authorized cursor. The broker commits before acknowledgement/fan-out; duplicates after network loss must not create duplicate messages or duplicate agent jobs. Keep heartbeat presence separate from the durable event log.

Store attachments as opaque objects under broker-assigned IDs. Record hash, byte size, safe display filename, media type, uploader, channel ACL and inherited labels. Support arbitrary byte downloads with limits and resumable chunks; verify hashes and finalize atomically. Do not render active HTML/SVG or execute uploaded files by default. Previews, antivirus and indexing run inside the same boundary. Authorized downloads and local caching should be visible, policy-controlled actions, with local encrypted storage and revocation-aware cache behavior where required.

Operational audit should record actor, action, object reference, decision, policy revision, approved release digest and run/provider identity, while minimizing raw payloads. A broker-owned append-only journal is useful but not tamper-proof against its administrator; stronger audit retention needs a separately controlled destination. Backup/restore, retention, deletion and legal hold are deployment requirements to be decided by the institution, not properties obtained from the SSH transport.

## Implementation sequence and acceptance gates

1. **Define protected domain types and pure authorization rules.** Introduce workspace/principal/team/channel/member/agent/run/attachment/context/release records. Separate visibility from classification. Test the full actor-operation-object matrix and no-existence-leak responses using synthetic fixtures.
2. **Build a minimal broker and SSH stdio bridge.** Prefer one portable Linux Rust binary with broker/bridge/worker subcommands and a line-framed JSON control protocol; binary attachments use bounded chunks with explicit encoding/length/digest. The broker uses kernel-bound identities and a protected single-writer JSONL journal. Test two distinct OS accounts, forged JSON identity, unauthorized channel reads, stream revocation, duplicate command IDs, disk-full/partial-write recovery and disconnect recovery. A same-account two-client smoke is transport evidence only.
3. **Human collaboration vertical slice.** Profiles, teams, invites, creator-owned channel deletion, text, file upload/download and current-channel presence. Validate multi-account permissions, filename/path traversal, symlink swap resistance, quota and interrupted upload recovery before agent execution.
4. **Owned agent vertical slice.** A per-owner/per-compartment worker wraps existing BioRouter agents or ACP. Wire command/status/result events to a Crew timeline and owner-only approvals. Assert another account cannot prompt, cancel, approve or use a guessed run/session identifier. Never give the broker a general-purpose shell.
5. **Mandatory privacy and worker isolation.** Enforce provider destination allowlists, inherited labels, compartment-filtered retrieval, public-worker readable mounts and egress. Use synthetic restricted markers and a fake public endpoint to prove zero leaked bytes across model requests, tools, previews, logs, titles and reconnect snapshots. Refuse protected execution if required OS enforcement is unavailable.
6. **Crew tools and desktop integration.** Add the sidebar tab, workspace selector and MCP/platform tools with explicit workspace/channel arguments where ambiguous. Reuse chat renderers and agent-event cards; keep shared messages separate from a personal session transcript. Preserve generated OpenAPI discipline for changed daemon APIs.
7. **HPC operation and production evaluation.** Separate persistent collaboration service from scheduler jobs. Test queued/running/completed/cancelled jobs, owner UID/account preservation, compute-node reconnect, scheduler limits, multi-hop and MFA paths, package installation, upgrades, backups, retention, restore and independent security review. PHI admission waits for the institution's approval of the concrete deployment.

This investigation ran no application builds or unit suites and did not verify live sandbox enforcement on either SSH host. Those are explicit feasibility/acceptance tasks; source presence and test names are not substitutes for execution evidence.
