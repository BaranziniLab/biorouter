# BioRouter Crew: SSH, identity, desktop and file integration investigation

> September 22 design update: [the implementation plan](implementation-plan.md) now follows the user's no-administrator, home-based deployment requirement, 2–50-user scope, cluster Public/Private toggle and built-in saved-SSH/MCP integration. It also contains the required three-user AWS/dev-app computer-use testing plan. Earlier deployment recommendations in this research snapshot are superseded; recorded source findings and probe results remain historical evidence, not rootless product acceptance.

Investigated 2026-09-21 against commit `314f3b268c24663a8696dbbbd5aa76a171d0fab8`. This is a source investigation and proposed design, not implemented functionality. Paths and line numbers below refer to that baseline. Remote measurements belong to the parent investigation; no SSH connections, builds or running-app changes were made in this lane.

## Principal findings

BioRouter has useful single-user agent, privacy, artifact, desktop and event-stream components, but does **not** currently have a first-class SSH connection manager or a multi-user chat service. CodeGraph was consulted first. Follow-up searches of `crates/` and `ui/desktop/src/` found no SSH/SFTP library integration, `ProxyJump`, `ControlMaster`, `ControlPath`, or `FileRouter` implementation. Existing SSH references concern secret protection, deployment through a manually established tunnel, and headless operation. “File Router” in the request should be treated as intended BioRouter functionality, not an existing module name.

An external HTTP backend, local filesystem bridge, share-link transcript, workspace UI-control socket and reusable MCP process are different capabilities from an authenticated shared Crew workspace. Crew should reuse their lower-level patterns without inheriting their single-user authorization model.

## Proposed SSH transport and identity

Use the installed native OpenSSH client for the first implementation. A typed Rust connection manager should own processes, framing, reconnect, cancellation and file-transfer streams; the Electron main process should own human authentication prompts. This retains institutional SSH configuration and avoids prematurely reimplementing institution-specific authentication in a Rust SSH library.

OpenSSH supports ordered `ProxyJump` lists; jump-host options generally require their own configuration stanzas. `BatchMode` suppresses interaction. `ControlMaster` multiplexes connections, and `ControlPersist` is an idle timeout, not a maximum authenticated lifetime. Control sockets should be stored in a private directory and distinguish host, port and user. These are documented mechanisms, not proof of compatibility with the two institutional deployments. [OpenSSH configuration manual](https://man.openbsd.org/ssh_config)

The SSH client also supports an askpass program and Unix-socket forwarding. Its `-G` option reports effective configuration. Prefer direct process argument arrays and fixed remote helper commands; do not interpolate room names, usernames, filenames or arbitrary text into shell commands. [OpenSSH client manual](https://man.openbsd.org/ssh)

The recommended path is:

```text
Crew UI -> local daemon Crew API -> native ssh -> remote crew bridge (Unix user)
                                                     |
                                                     v
                                    crew service Unix-domain socket
                                    (kernel peer UID -> member record)
                                                     |
                          messages, membership, attachments, durable event log

Owner's agent -> separate owner-scoped SSH process/session -> compute work
                                |
                     authorized activity projection -> channel
```

The bridge's socket peer identity must be obtained by the service from kernel credentials, not from `$USER`, a JSON username, nickname, forwarded HTTP header, or client-supplied UID. A raw TCP listener bound to localhost is reachable by other users on the server and does not prove which SSH account originated a request. A local HTTP port forward similarly does not itself establish a person's identity.

Use a service-issued workspace UUID and an immutable member UUID bound to the verified Unix identity at enrollment. Display the SSH username prominently and allow nickname/avatar customization. A username is unique only within its identity realm and may later be reassigned; a hostname can be an alias, load-balanced endpoint or rebuilt server. Store a workspace identifier, expected host identity and enrollment generation rather than relying on `user@host` as a permanent global key. Separate connections to the same workspace should converge after a verified handshake; identical usernames on different workspaces remain different people.

The Crew service must own its journal, snapshots and attachment objects; ordinary members get socket/API access, not write access to the storage directory. A group-writable journal defeats all application-level membership and creator-only deletion rules. A service account/approved institutional service install is the production model. A user-owned daemon can support a clearly labeled prototype where that owner is trusted with every byte, but is not an independent multi-user isolation boundary.

## MFA and multiple jump gates

Make authentication an explicit connection state machine: resolving configuration, verifying host, authenticating hop, awaiting human action, starting bridge, validating workspace, connected, reconnecting, reauthentication required, disconnected, failed. The UI should identify the intended workspace and available hop details; do not claim to know a hop from an ambiguous OpenSSH prompt.

Support keyboard-interactive challenges, Duo push/menu flows, TOTP entry, key passphrase prompts and security-key touches as human actions. A dedicated prompt surface must not feed these replies into any LLM, ordinary chat history, tool event stream, channel timeline, debug log, clipboard history managed by the app, or persistent configuration. A timeout/cancellation is an explicit connection outcome. Do not automatically retry MFA repeatedly and trigger account lockouts or push fatigue.

Start with a private authentication terminal as a compatibility fallback plus a structured askpass flow where supported. Keep the authentication TTY separate from the binary Crew protocol stream: complete authentication/master setup first, then open a non-PTY SSH exec channel for the bridge. Prompt handling and ControlMaster availability must be validated on supported macOS, Linux and Windows OpenSSH versions; where multiplexing is unavailable, use a persistent SSH exec with askpass or another explicitly tested client adapter rather than claiming parity.

Verify host keys at every hop using institution-provided fingerprints/host CAs or the user's known_hosts. A changed key blocks the connection with an actionable identity error; never use `StrictHostKeyChecking=no` to smooth over it. A new host trust decision is distinct from MFA and must be shown as such. Native SSH config can run `ProxyCommand`, `LocalCommand` or `Match exec`; Crew should only use a user-selected, trusted configuration and must never import an untrusted config embedded in an invitation.

Default agent, X11 and credential delegation forwarding off. SSH multiplexing should use an app-owned private socket directory, a per-connection key incorporating target account, destination, jump chain and policy realm, bounded idle persistence, and an independently enforced maximum authentication age. A constantly active chat can keep an idle timer from firing, so policy-triggered reauthentication must close the actual master and reopen authentication. Do not take over or kill the user's unrelated SSH master processes. A first implementation may use one connection per workspace and one independent channel per owner agent; pool only after isolation and lifecycle tests pass.

The parent investigation reports successful existing `BatchMode` authentication to both supplied hosts, Narrows home storage on NFS with Slurm available, Leo home storage on ZFS, and no `biorouter` executable on PATH at either. These findings do **not** test interactive MFA, new-device authentication, multiple ProxyJump hops, security-key prompts, or forced reauthentication. Those remain explicit acceptance gaps and must be exercised with synthetic data in an approved test environment.

## Storage, teams, channels and agent isolation

Keep workspace members, profiles, teams, invitations, channel membership, creator ownership, durable events, blob metadata, policy versions, grants, audit records and server preferences authoritative on the service. Follow the user's portability preference: JSONL protocol frames and a canonical single-writer JSONL journal, with regular attachment files; no database server, Redis or container requirement. Keep local SSH profile aliases, pinned workspaces, layout and policy-permitted caches on the client. Store local secrets in an OS credential store. For restricted workspaces, disable offline content caching by default and make any allowed encrypted cache policy-controlled. Store socket files on a local runtime filesystem, not NFS.

The journal needs server-assigned sequences, versioned schemas, durable commit acknowledgements after the selected fsync policy, idempotency keys and strict replay validation. Write blobs to temporary service-owned paths, fsync and rename before appending a committed attachment event; garbage-collect unreferenced objects after a recovery grace period. Recovery may handle a demonstrably incomplete final record, but interior corruption must stop startup with an actionable error rather than silently skipping membership or policy changes. Periodic atomic snapshots and derived indexes may accelerate replay/search without becoming the authority. Single-writer ownership must be enforced across process restarts; file-lock and fsync behavior on the actual NFS/shared filesystem is an acceptance requirement, not a consequence of choosing text. The service must never let every client append directly to the journal. Backups, compaction and retention rewrite are service operations with recoverable manifests and audit records.

Discover only accounts that have enrolled in Crew and are visible under directory policy. Do not publish the whole OS account directory or assume SSH access grants access to every team. Membership and invitation acceptance are separate from SSH authentication. Default room visibility is team-scoped; “public room” must not mean public internet or permission to use a public model. Use distinct language such as “team-visible” for discoverability and “Public/Private data” for sensitivity.

A channel creator alone may remove/archive their channel, per the requested rule; server operations such as emergency suspension and retention/legal-hold enforcement are explicit administrator powers, not silent creator impersonation. Decide creator departure and ownership transfer before rollout. Team membership removal must revoke subscriptions, search/context reads, file reads and new agent invocations immediately on the server. Already downloaded bytes cannot be recalled; the UI must not imply otherwise.

Each agent run has an immutable owner principal, workspace, team/channel target, provider binding and scoped capability. Only that owner can prompt, approve, interrupt, change provider or cancel the run. Other channel members can observe the authorized projection and discuss results, but channel text mentioning an agent never grants control. A service running as a shared account must not execute arbitrary user commands as that service account. Owner jobs run in an owner-authenticated SSH process or an institution-approved job broker that preserves the Unix UID; asynchronous scheduler work is submitted as that owner.

Map an agent run to a private owner Session and publish selected structured events into the Crew channel: requested action, tool start/progress/completion, resulting files and final answer. Redact credentials and apply content/affiliation policy before publication. Do not blindly publish raw stderr/environment/prompt/hidden model reasoning. Prefer “agent activity” over a promise that every internal byte is visible. Use stable run/event IDs, idempotency keys, sequence cursors and reconnect replay; presence is ephemeral and must not stand in for event durability.

Agents may search other channels only within an explicit permission scope and current membership. Default retrieval scope is the current channel. An owner can opt into selected channels or an approved workspace search scope; every retrieved item carries source channel, author, timestamp, classification and source event ID. A cross-channel context bundle is a versioned snapshot whose classification is the union of all inputs. Membership/policy checks run at retrieval, model dispatch and result publication. Private material cannot enter public-model requests or public channels through quotes, summaries, filenames, thumbnails, embeddings, search snippets or tool errors. An agent cannot declassify data by paraphrasing it.

## Attachments and downloadable files

Add an attachment service rather than passing local paths through existing messages. Upload creates an opaque upload ID tied to workspace/channel/principal, streams bounded chunks, validates declared size and checksum, supports retry/resume, then commits a blob record and event atomically. Downloads authorize membership and sensitivity for each request/range. Content bytes remain on the same approved host/storage plane and travel over the authenticated SSH bridge. Avoid public object-store URLs in private workspaces.

Use opaque blob identifiers and safe content disposition. Preserve an original display filename as metadata; never use it directly as a server path. Reject traversal, symlink and hardlink escape attacks, devices, FIFOs and overwrite ambiguity. Quotas, transfer cancellation, interrupted-upload cleanup, disk-full handling and retention are required. Arbitrary binary attachments may be stored/downloaded without inline execution. Render only supported previews in a sandbox, with HTML/SVG active content isolated and no external network fetches for private media. Large scientific datasets should support policy-checked file references alongside uploaded snapshots; a reference is not a guarantee that another Unix user can read the target.

Every upload, remote-path attachment, generated file and download must carry classification and provenance. File previews must not use the current local Electron path resolver to interpret a remote path. Bind artifact links to an attachment ID and workspace, so `/home/wanjun/results.csv` on Leo cannot accidentally resolve to a same-named local or Narrows path. Reuse existing canonicalization and refusal behavior as implementation guidance, not as proof that new remote blob operations are safe.

## UI and API proposal

The Crew page should present a workspace switcher with SSH status, selected team, channels, people and files. A persistent header shows verified SSH identity and the data boundary; channel visibility and provider destination are separate chips. The composer has explicit “Message channel” and “Ask my agent” actions, an owner agent/model selector, file drop/upload progress, and a visible context-scope picker. Each agent activity card identifies its owner and run; other members see read-only controls. Profiles and avatars are workspace-specific unless a user explicitly copies them elsewhere.

Implement a dedicated `crew` domain module or crate for records, policy and durable events, plus a small portable Linux service/bridge executable. Use bounded JSONL frames for control and streaming events over SSH stdio, and a documented bounded chunk transfer format for binary attachments. Add local `/crew/connections`, `/crew/workspaces`, `/crew/...` endpoints or an equivalently typed IPC façade, keeping connection credentials inside the trusted local process. Add remote protocol operations for handshake, teams, invitations, channels, membership, event append/read/subscribe, attachment begin/chunk/commit/read, scoped search, owner-run registration and audit. Generate OpenAPI through the repository's existing workflow for local HTTP additions; do not hand-edit generated clients.

Expose Crew agent tools as a built-in extension backed by the same policy engine: list authorized workspaces/channels, read/search context, post a message, attach a file, register/project own agent run. Slash commands such as `/crew send`, `/crew context`, `/crew files`, and `/crew agent` should resolve workspace/channel explicitly and require a deterministic handler. Agent-authored sending to a human room remains a permissioned capability and retains the user's configured approval behavior. Opening a channel or receiving a message never authorizes a send.

The local daemon's own privileged API and external-backend user-action key must never be shared with the Crew remote service or other members. The Crew service issues narrow capabilities for the active principal and workspace, and neither the service nor another member receives a user's model-provider credentials. ACP can be used inside an owner's agent adapter, but it does not replace transport authentication, team ACLs, durable chat events or ownership policy.

## Focused acceptance plan

1. Native SSH matrix: direct connection, one and multiple jump hosts, distinct usernames/ports per hop, known-host success, unknown-host confirmation, changed-key refusal, keyboard-interactive MFA, TOTP, Duo timeout/decline, key passphrase, security-key touch, cancelled prompt, disconnect and reauthentication. Test every supported desktop OS; report each actual path separately.
2. Principal matrix: two Unix UIDs with the same chosen nickname cannot impersonate one another; a bridge that lies about its UID is ignored; a localhost TCP caller cannot bypass identity; an unaffiliated local account cannot open an authorized workspace session. Check username reassignment and host rebuild behavior.
3. Team/channel matrix: enrolled users can create/join only authorized teams, private channels cannot be enumerated by outsiders, only the creator deletes a channel, and member removal closes streams and blocks file/context reads while connected.
4. Owner-agent matrix: two owners can run agents concurrently in one room; the other owner cannot prompt/cancel/approve/replace the provider. Each process/scheduler job has the expected Unix UID. Room text containing fake instructions does not activate tools.
5. Privacy matrix: cross-channel context, model switching, outbound messages, file previews/downloads, summaries, search snippets and reconnect replays preserve labels; local privacy-off setting cannot weaken server policy. Institutional affiliation restrictions remain enforced even between two private providers.
6. Durable chat/files: simultaneous sends, duplicate retry, monotonic ordering, restart replay, slow consumer resync, interrupted multi-GB upload, digest mismatch, quota/disk-full, path/symlink tricks, active-content attachments and authenticated range downloads.
7. Cluster policy: approved long-running service location, no compute-heavy work on login nodes, scheduler execution as owner, validated journal and socket storage, backup/restore, service upgrades, process recovery after logout and revocation. Narrows NFS home requires explicit single-writer/fsync/rename validation and an approved storage choice, not a hidden default.

This source investigation did not run these tests. The parent feasibility report should distinguish tests completed with synthetic fixtures from all remaining acceptance items.
