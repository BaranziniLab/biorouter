## Work item 1: the Linux first-launch hang (done)

**What failed.** In `verify`, `smoke_rpm` (in `scripts/smoke-test-release-artifacts.sh`) launched the
packaged app in a `rockylinux:9` container under Xvfb, sent SIGTERM, and waited forever.

**Root causes**, both reproduced with the built packages in Docker:

1. zenity rejected the approval prompt (exit 255, "This option is not available") because the prompt
   text contained an en dash (between "32" and "4096") and the container had no UTF-8 locale. `nativeSecretPrompt.ts`
   treated every non-zero exit as a user cancel, so startup failed with "Shared daemon startup
   cancelled".
2. The fatal startup handler then called the synchronous `dialog.showErrorBox`. On Linux it runs a
   nested GTK loop that ignores SIGTERM, so only SIGKILL could end the app.

**What `93576fdff` changed.**

- All native prompt text is ASCII, with a test that fails on any non-ASCII prompt text.
- On Linux, zenity's stderr is captured. Exit 1 is still a cancel; other codes, "cannot open display"
  and a failed spawn now produce an error that names zenity.
- The prompt process is closed on `will-quit` and process exit, so no orphaned dialog is left behind.
- New `ui/desktop/src/utils/fatalStartupError.ts`: on Linux the fatal error uses the non-blocking
  `dialog.showMessageBox` and quits when it closes, so SIGTERM still works. macOS and Windows keep
  the synchronous box.
- New `scripts/smoke-linux-desktop.sh`, run inside both the DEB and RPM containers with `LANG` unset
  and every wait bounded. `smoke_mac` got its own `--user-data-dir` (on macOS, Electron ignores
  `HOME` for userData) and kills every descendant it started.

**Still to do for work item 1:** its smoke cases 1 and 2 expect the zenity approval prompt on first
launch. Work item 2 removes that prompt, so those cases must be rewritten (listed under work item 2).

Two weaknesses found along the way, both addressed by this commit and worth keeping in mind: the old
macOS and DEB smoke checks only proved the process was alive after 12 seconds (an app stuck at a
dialog passes that), and the old macOS smoke left an orphaned osascript secret dialog on the
operator's screen and wrote into the operator's real `~/Library/Application Support/Biorouter`.

## Work item 2: remove the approval secret

### Why it existed

The daemon (`biorouterd`) only accepts actions that need a person, such as Crew approvals and private
chat access, when the request carries an `X-User-Action` proof. Up to 1.91.2 the app minted a random
key at each launch and handed its digest to the daemon on stdin; the daemon died with the app, so the
key never needed storing. In 1.92.0 the daemon is shared and outlives the app (Crew stays connected
after quit, and `biorouter crew` shares it), so a reopened app had to prove itself to a daemon it did
not start. 1.92.0 solved that by making the person hold the key. The owner rejected that.

### The design (binding)

Whoever starts the shared daemon (the desktop app or `biorouter crew`) mints the key, hands the
digest to the daemon on stdin as before, and saves the key in a file only the user can read. The app
and the CLI read that file and never ask anyone. A daemon that cannot be used with the file's key is
replaced. Windows is unchanged (the shared daemon is off there). The Crew **vault passphrase** prompt
is a different thing and stays.

**Key file contract.** Both the Rust and the TypeScript sides already implement this; do not change
it without changing both.

- **Path:** `<state>/daemon/user-action-key.json`, next to `runtime.json`. `<state>` is
  `$BIOROUTER_PATH_ROOT/state`, else `$XDG_STATE_HOME/biorouter`, else `~/.local/state/biorouter`, on
  macOS and Linux alike. Rust: `daemon_runtime::user_action_key_path()`. Desktop:
  `path.join(path.dirname(daemonRuntimePath()), 'user-action-key.json')`.
- **Format:** exactly `{"version":1,"profile_id":"<uuid>","instance_id":"<uuid>","pid":<number>,"key":"<64 lowercase hex>"}`.
  Unknown or missing keys are rejected. At most 16 KiB.
- **Permissions:** directory 0700 owned by the user; file regular, not a symlink (`O_NOFOLLOW`), owned
  by the user, mode exactly 0600, one link. Rust reads with `read_private`, the desktop with
  `privateJson`.
- **Atomic write:** Rust `daemon_runtime::write_private`. Desktop: a `.<name>.<random>.tmp` file opened
  `O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW` 0600, write, fsync, rename, fsync the directory.
- **Start order (launcher only):** generate the key; spawn `biorouterd agent` with
  `BIOROUTER_SHARED_DAEMON=1`, digest on stdin, close stdin; poll `runtime.json` until its `pid` is the
  child's and its identity checks out; write the key file bound to that `instance_id` and `pid`;
  verify with `GET /crew/connections` (`X-Secret-Key` plus `X-User-Action`). On any failure after the
  write, kill the child and remove the key file if the instance still matches.
- **Removal:** the daemon removes the file in `RuntimeOwner::drop` when the instance matches. It never
  writes it.
- **Reading:** accept the record only if `version == 1`, `profile_id` and `instance_id` and `pid` match
  `runtime.json`, and the key is 64 lowercase hex. Poll every 100 ms for up to 5 s
  (`KEY_FILE_GRACE`), because a starter writes the file just after the daemon publishes.
- **Unusable daemon:** no matching key file after the grace, `user_action_installed` false, or a 403
  on `GET /crew/connections`. The app, and the CLI when allowed to start one, stop it and start a
  fresh one. With `--no-start` the CLI refuses with code `crew_daemon_needs_restart` and the text:
  "The running Biorouter daemon was started by an older version of Biorouter, so this command cannot
  use it. Run biorouter crew daemon stop, then run this command again."
- **Version mismatch (desktop only):** after identity checks, `GET /system_info` over the socket with
  `X-Secret-Key`, compare `app_version` with `app.getVersion()`, and replace the daemon if they differ.
  The CLI does not do this, so an older `biorouter` on the PATH cannot stop a newer app's daemon.
- **Stopping without a key:** verify `runtime.json` and `/daemon/identity` (same pid and instance),
  confirm the process name is `biorouterd` (Linux `/proc/<pid>/comm`; macOS `ps -o comm= -p <pid>`),
  SIGTERM, wait up to 15 s, check the name again, SIGKILL, wait 3 s, otherwise fail with "Biorouter
  could not stop the old background service (process <pid>). Quit it, then open Biorouter again."
- **Two starters at once:** only one daemon gets `owner.lock`. The launcher whose child exited looks
  again and attaches to the winner through the normal reading path.
- **CLI flags:** `--approval-key-stdin` stays accepted and is never required; when set and stdin is
  not a terminal it reads and discards one line (so old scripts that send a secret then a passphrase
  keep working). New `--passphrase-stdin` reads the vault passphrase from the first line and conflicts
  with `--approval-key-stdin`. `daemon stop` needs no secret. `daemon start` when one is running
  fails with "A Biorouter daemon is already running for this profile. Stop it first with biorouter
  crew daemon stop."
- **Credential guard:** `"**/daemon/user-action-key.json"` is in `DEFAULT_SECRET_PATTERNS` so a model
  is refused a casual read. This is accident prevention, not a security boundary.
