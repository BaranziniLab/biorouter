Security

Where Biorouter keeps your credentials, which files it refuses to read, and how much the agent may do without asking.

Credentials

Provider API keys and other secrets go to your operating system's credential store, not to config.yaml. Biorouter reads the store once per process and keeps the values in memory, so one authorization covers the whole run.

Credential storeWhat to expect
macOS
Keychain		macOS asks for your password the first time a program reads the item. Choose Always Allow. The background service (biorouterd) and the command line (biorouter) are separate programs, so each asks once, and a program is never asked about an item it created. The grant survives updates.
Windows
Credential Manager		No prompt. Windows protects the entries for your account.
Linux
Secret Service		GNOME Keyring or KWallet. No prompt on a desktop session, which opens the store when you log in.

Where no credential store answers, as on a Linux server, over SSH or in WSL, Biorouter keeps secrets in secrets.yaml beside config.yaml instead. Set the environment variable BIOROUTER_DISABLE_KEYRING to any value to choose that file on purpose. Prefer the credential store where there is one. Crew device keys are the exception: they never go to secrets.yaml, and on a computer with no credential store Crew keeps them in an encrypted vault instead; see Keep device keys in an encrypted vault.

On macOS and Linux, Biorouter creates secrets.yaml readable and writable only by your account, creates a missing folder for it that only your account can open, and tightens an existing file the next time it writes it. Anyone who can act as your account, or as root, can still read the file.

An environment variable named after a key, such as OPENAI_API_KEY, always wins over the stored value.

The secret guard

A model with a shell can read any file you can. The secret guard refuses a tool call that reads or names a file whose purpose is to hold a credential. It works in every chat, in every permission mode and on every model, and it has no switch.

It protects these names in any folder:

KindNames
Secret files.env, .env.*, secrets.* (Biorouter's own secrets.yaml included)
Keys and certificatesSSH private keys such as id_rsa and id_ed25519, *.pem, *.p12, *.pfx
Tool logins.aws/credentials, .codex/auth.json, .claude/.credentials.json
More tool logins.netrc, _netrc, .pgpass, .git-credentials, .docker/config.json, .kube/config, .config/gh/hosts.yml
  • Commands are read as the shell reads them. ~, variables, globs and cd are resolved before the path is judged, so cat ~/.aws/credentials and cd ~/.aws && head cred* are both refused.
  • A match is refused whether or not the file exists. A command that only names a protected file, such as echo X=1 > .env, is refused too.
  • Results are checked as well. When a credential still reaches a tool result, the guard replaces it with a marker such as [REDACTED:aws-secret-access-key] before any model sees it. It recognizes private key blocks, AWS keys, common provider tokens, and values under names such as *_API_KEY or *_TOKEN.

To open one protected file on purpose, add a negation to .biorouterignore: the project's own file for paths inside the project, or ~/.config/biorouter/.biorouterignore for every path. For example, !**/.env.example in the project's file reopens its example env files. Any other pattern you add there keeps those files from the agent too.

The guard stops mistakes, not a determined attacker. It cannot see a path a program builds while it runs, a recursive read of a parent folder such as grep -r key ~/.aws, or text inside a screenshot.

Secrets for applications

An application can hold its own secrets, apart from your provider keys. Its vault capability is off unless the application's manifest names each secret, for example "vault": { "encrypted": ["SPOKEAGENT_PASSCODE"] }. The values are stored encrypted in the application's .vault/ folder, and the application refers to each one by name as {{vault:NAME}}. Biorouter fills in the value when a tool runs, so the value never reaches the model. An exported application leaves .vault/ behind.

Dictation

Next release. Local dictation arrives in the release after v1.94.1.

Voice dictation runs on this computer with a speech model you install once. Audio is not sent to a cloud service and is never saved; the cloud dictation route of earlier releases is removed. Your dictionary of spellings is stored on this computer too.

  • The agent's dictionary tools are off until you choose. They come with the Dictionary capability, which new chats get only when Suggest dictionary words from my chats is on. By default, a term the agent adds goes live at once only when you asked for it, or answered the agent's offer of it; anything else waits for you to accept it.
  • Private terms stay in private chats. A term you add from a private chat is private by default, and it shapes dictation only into chats on private models, never into a public chat or another institution's model.
  • An administrator can narrow it. A managed policy can turn dictation off, allow only approved speech models, or stop the agent from writing the dictionary.

Permission modes

The permission mode sets how much the agent does without asking. Choose it in Settings → Chat → Approvals, with /mode at the classic terminal prompt, or in the settings menu of biorouter configure. It is stored as BIOROUTER_MODE.

ModeValueWhat the agent does
AutonomousautoUses tools and edits, creates or deletes files without asking first. This is the default.
ManualapproveAsks before every tool call, unless you chose Always Allow for that tool.
Smartsmart_approveRuns calls with low risk and asks before the rest.
Chat onlychatNo tools and no extensions. The model only answers.

What asks in every mode

A few actions ask even in Autonomous, and no hook can answer for you:

  • Writing or deleting under a protected system folder, your home folder itself, or a credential store such as ~/.ssh.
  • A shell command that makes SSH trust a server's host key nobody checked, such as ssh, scp or rsync -e with StrictHostKeyChecking=accept-new or no, or a known-hosts file other than the default.
  • Reading, saving or deleting a global memory, which every chat on the computer shares, and clearing every global memory, which cannot be undone. No call reads all global memories at once; each category is read and approved separately.
  • Observing or controlling the desktop with Biorouter Copilot.

An approval never reopens a call that was already refused, whether by your own Never allow, by a managed policy or by the block on destructive commands.

A permission card nobody answers does not wait forever. After its window, 5 minutes for a folder card and an hour by default for a tool card (BIOROUTER_CONFIRMATION_TIMEOUT_SECS), it turns into a line reading Expired: ask again, the call is not run, and the model is told why. A late click approves nothing. To go ahead, ask again in the chat.

Biorouter Copilot asks for each task

Turning on Biorouter Copilot in Settings → Chat → Capabilities does not give it your desktop. Before its first capture or action for a request, Biorouter asks for approval that names the model and provider, where their data goes, and the computer to control. With a public model, the approval says that screenshots and application text can be sent to that provider. You choose Allow, which lets it look and control, or Only let it look, which lets it see your apps and change nothing. The approval covers that one request and ends when the reply finishes, when you stop it, or when the model changes. It never reaches Biorouter's own windows, password fields or system security prompts. Chat only refuses every Biorouter Copilot tool.

On macOS, Accessibility and Screen Recording belong to an app named Biorouter Copilot inside Biorouter, never to Biorouter itself, so a command the agent runs in a shell cannot use them. Request access in Biorouter Copilot's setup has macOS ask for both.

Managed policy

An administrator can install a policy file that outranks your own settings. It can deny a tool, require approval for it or approve it in advance, and it can add hooks that always run. It can also turn local voice dictation off or narrow it, through a dictation: block. A deny holds in Autonomous mode too, and the call reports “Blocked by your organization's managed policy.”

ComputerPolicy file
macOS/Library/Application Support/Biorouter/managed-policy.yaml
Linux/etc/biorouter/managed-policy.yaml
Windows%ProgramData%\Biorouter\managed-policy.yaml
 
permissions:
  deny:
    - "developer__shell"
  ask:
    - "memory__.*"
  allow:
    - "developer__text_editor"

A tool name matches exactly or as an anchored regular expression. Deploy the file with your device management tools, such as Jamf, Ansible or Group Policy.

The dictation: block arrives with local dictation in the release after v1.94.1. Each of its keys only narrows dictation, and writing true is the same as leaving a key out. An eighth key, external_engine, is accepted and has no effect in this release.

dictation:
  enabled: false                 # dictation off everywhere
  capture: false                 # no live microphone; a recording can still be transcribed
  model_downloads: false         # speech models come only from models_dir
  allowed_models: [whisper-small.en-q8_0]
  models_dir: /var/lib/biorouter/dictation/models
  dictionary: false              # no dictionary; plain transcription still works
  dictionary_agent_writes: false # the agent cannot write the dictionary

With enabled: false, people see “Dictation is turned off on this computer by your organization's managed policy.” The other keys have refusals of their own. An unknown key, an empty dictation:, a value of the wrong type or a relative models_dir turns dictation off with a warning that names the key, while the rest of the policy still applies. The dictation block lists every key and refusal.

  • On macOS and Linux the file is read only if it and its folder belong to root or to you, and neither the group nor others can write to them. On Windows the %ProgramData% location is trusted, and ownership is not checked yet.
  • A file that fails the check or does not parse is ignored with a warning, and Biorouter runs as usual. Dictation is the one exception: if a policy file exists but cannot be trusted, read or parsed, dictation is turned off while the rest of the policy is ignored.
  • BIOROUTER_PATH_ROOT moves the file into <root>/managed/.

Shell sandbox

The shell sandbox is off by default. With the environment variable BIOROUTER_SHELL_SANDBOX set (it has no effect in config.yaml), each shell command runs in an operating system sandbox that lets it write only to the working folder and the temporary folder, and blocks outbound network where the kernel allows it. biorouter doctor shows which parts your computer gets. The sandbox is Seatbelt on macOS, and Landlock with seccomp on Linux, or bubblewrap where the kernel lacks them. Windows has no shell sandbox yet.

  • auto (or 1, true, on) uses the best sandbox available. Where there is none, it warns once and runs the command anyway.
  • strict refuses to run a command when a full sandbox is not available.
  • BIOROUTER_SHELL_SANDBOX_NETWORK=1 lets sandboxed commands reach the network.

Apart from the sandbox, a block that is always on refuses a few commands that cannot be undone, such as rm -rf /, disk wipes and fork bombs, in every mode.

Patient data

These controls decide what the agent may do on your computer. Where your data goes depends on the model. For patient data, use a local or institutional model, and read Private and public for what keeps a private chat away from public models and what it does not cover.
