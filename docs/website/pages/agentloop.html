The agent loop

Each request runs as a loop of model calls and tool calls. Biorouter runs the loop, so it decides what the model sees and what may run.

How a turn runs

StageWhat happens
ReceiveOne turn runs in a chat at a time. A message you send while it runs waits in a queue; see Steering a running turn. Commands such as /goal and /schedule are handled before the model is called.
Build contextThe system instructions (base instructions, permission mode, date, guidance from each extension, any workflow instructions), the tool list, the skills in use, up to five passages from a knowledge base you referenced with /kb:, a map of the working folder of up to about 2,000 tokens, and the conversation so far. At 80% of the model's context window, older turns are summarized for the model; your history is kept in full.
Call the modelThe reply streams back as text, tool calls, token counts and a reason for stopping. A reply cut off at the length limit is continued up to 12 times.
Permission gateEach tool call is checked by the administrator's managed policy, the command policy, your permission mode and any hooks. Deny is checked before ask, and ask before allow; an administrator's deny or ask always wins. A few destructive commands are refused in every mode. The modes are on the Security page. Up to 8 tool calls run at once; writes to the same file run one at a time.
Run and returnThe result goes back to the model. A large result is saved to a file, and the model gets a preview. Private keys and stored credentials in a result are withheld. An error goes back as an error the model can act on, not as the end of the turn.
FinishWhen the model answers without a tool call, the active checks run: a workflow's response schema, Stop hooks and a /goal. A failed check sends the turn back to work. A Stop hook can do this 5 times, and a /goal is dropped at the limits in Goals. A workflow's retry checks run after the chat finishes, and a failure starts the run again from the beginning. The whole turn is saved to the chat.

Loop limits

Several checks watch a long turn for repetition and runaway cost. Most warn the model first.

  • Exact repeats. The same call with the same arguments: a warning at 3, and the fifth identical call is refused.
  • Near repeats. Nearly the same call, or two calls taking turns: a warning at 4.
  • Repeated failure. The same failure from the same tool: a nudge at 3, then “change approach or ask the user” at 5. After 6, the next call to that tool is refused.
  • Failures in a row. Failed calls to any tool: a nudge at 3. At 6, the model is told to change route or hand the work back to you.
  • Stalls. A check for a stall after 30 actions in one turn, then every 10. A confirmed stall gets a short grace period to answer, then the turn stops.
  • Work without your input. The turn stops at 100 turns or 200 tool calls and names the limit. Quick reasoning effort halves both, and Deep doubles them. Set BIOROUTER_MAX_TURNS or BIOROUTER_MAX_TOOL_CALLS to change them; the command line also takes a turn limit for one run (see Command line). A message you add to the turn resets both counts.
  • Reply budget. A limit on the time, tokens or cost of one reply. Off by default. Set BIOROUTER_REPLY_BUDGET_SECONDS, BIOROUTER_REPLY_BUDGET_TOKENS or BIOROUTER_REPLY_BUDGET_USD for a warning, a request to wrap up, then a stop.

Delegation and several chats

Subagents

Ask in plain language, for example “Have a subagent check the QC report while you draft the methods.” A subagent is a separate chat that runs one task and reports back to the chat that started it. Several can run one after another or in parallel. In the desktop app each one opens in a background tab marked as a subagent, where you can read it as it works, type to steer it, and stop it. Closing the tab does not stop it. If you typed into it, the parent is told.

  • A subagent has the parent's extensions unless you name fewer, 25 turns (BIOROUTER_SUBAGENT_MAX_TURNS) and 5 minutes by default.
  • It cannot start subagents of its own, change the parent's extensions, or change schedules.
  • It never moves work across the privacy boundary. A public chat cannot start a subagent on a private model, and a private chat cannot start one on a public model. A public subagent is given no private data extensions, and the parent is told which were left out. See Private and public.

The subagent tool is offered only when all five of these hold. If a request for a subagent gets an ordinary answer, check them in order.

  1. The permission mode is Autonomous (the default).
  2. The model's name does not start with gemini.
  3. The chat is not itself a subagent.
  4. At least one extension besides Workspace Control is turned on.
  5. The chat is not a built app that delegates to its own worker profiles.

Workspace Control

Workspace Control lets the agent work across your chats. It is on by default. To turn it off for new chats, use Settings → Chat → Capabilities in the app, or run biorouter configure in a terminal and choose Toggle Extensions, then workspace. The agent can:

  • open a new chat in a tab, a split pane or a new window. New tabs open in the background and start in your working folder.
  • list what is running, and read another chat as a summary, a transcript, its tool calls or a subagent's starting instructions. A public chat cannot read a private one.
  • send a prompt into another chat and wait for it to finish.
  • change another chat's extensions, skills, model or knowledge bases.

Some changes show a confirmation card in every permission mode: giving a chat an extension that can start programs, removing one that matters for security, switching its model provider, or adding a skill. The changed chat shows who changed what. The first time a private chat writes into a public chat, Biorouter shows you what it would send and asks first.

Steering a running turn

You do not have to wait for a turn to finish. A message you send while it runs waits in a queue at the text box, with two choices:

  • Add now adds the message to the running turn without stopping it. With the text box empty, Cmd+Enter (Ctrl+Enter on Windows and Linux) does the same for the first message in the queue.
  • Stop & send stops the turn and sends the message as a new one.

An added message reaches the model at the next safe point. A running tool is never cut off for it. If an approval card is waiting, the message waits until you answer the card, because a message never answers a card. If the turn ends before the model reads it, the message stays in the chat marked as not answered. A message with attachments cannot be added to a running turn; it waits, or you can use Stop & send.

A browser opened with biorouter serve cannot add messages to a running turn, and neither can any other client of that service. Stop still works. Use the desktop app. biorouter session attach can add to a running turn only on a service started with a user action key; see Command line.

Goals: /goal

/goal keeps the agent working until a condition you can check is true.

/goal the notebook runs with no errors

Work starts at once. Each time the agent tries to finish, an evaluator reads the recent part of the chat and checks the condition. If it is not met, the evaluator's feedback goes back to the agent and the turn continues. After 20 evaluations, or when the evaluator gives nearly the same feedback 3 times in a row, the goal is dropped and the agent reports what it did, what is unfinished and what stands in the way.

/goal on its own shows the active goal, and /goal clear removes it. The goal is saved with the chat, so it survives a restart. Write the condition as an end state the agent can show, such as a file that exists or a test that passes.
