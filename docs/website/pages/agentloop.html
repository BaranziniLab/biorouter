The agent loop

Each request runs as a loop of model calls and tool calls. Biorouter runs the loop, so it decides what the model sees and what may run.

How a turn runs

StageWhat happens
ReceiveOne turn runs in a chat at a time. A message you send while it runs waits in a queue; see Steering a running turn. Commands such as /goal and /schedule are handled before the model is called.
Build contextThe system instructions (base instructions, permission mode, date, guidance from each extension, any workflow instructions), the tool list, the skills in use, up to five passages from a knowledge base you referenced with /kb:, a map of the working folder of up to about 2,000 tokens, and the conversation so far. Past the compaction limit in Keeping a long task affordable, older turns are summarized for the model; your history is kept in full.
Call the modelThe reply streams back as text, tool calls, token counts and a reason for stopping. A reply cut off at the length limit is continued up to 12 times.
Permission gateEach tool call is checked by the administrator's managed policy, the command policy, your permission mode and any hooks. Deny is checked before ask, and ask before allow; an administrator's deny or ask always wins. A few destructive commands are refused in every mode. The modes are on the Security page. A permission card nobody answers in time turns into one muted line, Expired: ask again, with no buttons. Up to 8 tool calls run at once; writes to the same file run one at a time.
Run and returnThe result goes back to the model. A large result is saved to a file, and the model gets a preview. Private keys and stored credentials in a result are withheld. An error goes back as an error the model can act on, not as the end of the turn.
FinishWhen the model answers without a tool call, the active checks run: a workflow's response schema, Stop hooks, a /goal, and monitors set to check as the turn ends (see Decision models). A failed check sends the turn back to work. A Stop hook can do this 5 times, and a /goal is dropped at the limits in Goals. A workflow's retry checks run after the chat finishes, and a failure starts the run again from the beginning. The whole turn is saved to the chat. A turn that fails shows its error once. When the failure can be retried, the error has a Retry button that sends the message again.

Loop limits

Several checks watch a long turn for repetition and runaway cost. Most warn the model first.

  • Exact repeats. The same call with the same arguments and no changing result: a warning at 3, and the fifth identical call is refused. New successful results reset the count.
  • Near repeats. Nearly the same calls, or a repeating sequence of calls, with no progress: a warning at 4 and a persistent cycle is refused at 8. Changing successful results and waits on running work reset the count.
  • Repeated failure. The same failure from the same tool: a nudge at 3, then “change approach or ask the user” at 5. After 6, the next call to that tool is refused.
  • Failures in a row. Failed calls to any tool: a nudge at 3. At 6, the model is told to change route or hand the work back to you.
  • Stalls. A check for a stall after 30 actions in one turn, then every 10. A confirmed stall gets a short grace period to answer, then the turn stops.
  • Work without your input. Ordinary chats have no fixed turn or tool-call limit by default, and existing positive limits are kept.
  • Max turns. To change it, open Settings → Chat → Approvals and choose Unlimited, or choose Set a limit and enter a positive whole number. An empty or invalid entry keeps the saved setting.
  • Limits in configuration. BIOROUTER_MAX_TURNS and BIOROUTER_MAX_TOOL_CALLS set the two limits, and 0 removes either one. The command line also takes a turn limit for one run (see Command line). Quick reasoning effort halves positive limits and Deep doubles them; Unlimited stays unlimited. A message you add to the turn resets both counts.
  • Reply budget. A limit on the time, tokens or cost of one reply. Off by default. Set BIOROUTER_REPLY_BUDGET_SECONDS, BIOROUTER_REPLY_BUDGET_TOKENS or BIOROUTER_REPLY_BUDGET_USD for a warning, a request to wrap up, then a stop.
  • Usage limits. A limit for one chat, a default for every chat, and a monthly limit, each in dollars, tokens or both. All are off by default. Set a chat's own limit from the cost at the lower right of the composer, and the other two in Settings → App → Usage. A chat's limit counts its subagents. At 80% the chat shows one notice, and the turn ends before the model request that would pass a limit. A chat at its own limit, or any chat once the month is at its limit, starts no subagent. While the month is at its limit, scheduled runs and Crew tasks do not start, and a chat at its own limit cannot start a Crew task either. Decision models count toward a limit, but a limit never stops them.

Keeping a long task affordable

Every request carries the whole conversation, so a tool result that stays in the chat is paid for again by every later request.

  • Large results. A tool result over 10,000 tokens (BIOROUTER_LARGE_RESPONSE_TOKENS) is saved in full to a file under .biorouter/tool-output/ in the working folder. The chat keeps a preview of about 2,000 tokens and the file's path, and the agent reads the file for the rest.
  • Older results. Older tool results leave the model's copy of the chat in batches, before compaction is needed. Your history keeps them in full.
  • Compaction. The chat is compacted when it passes the lower of 80% of the model's context window (BIOROUTER_AUTO_COMPACT_THRESHOLD) and 200,000 tokens (BIOROUTER_AUTO_COMPACT_MAX_TOKENS). The limit is checked before every request of a long reply, so one turn with many tool calls cannot grow far past it.
  • Waiting on a job. For a long external job, the agent can call watch_job, which ends the turn and resumes the chat once when the job finishes, instead of making a model request for every check.

Decision models

A decision model is a fast model that answers a fixed question, yes or no, one of named options or a level on a scale, with the probability of each answer instead of text. Decision models are optional: Biorouter works with one chat model and none of them. Baseten and Ollama serve them; see Public: API providers. A chat uses them in three ways:

  • Monitors. A monitor asks one question about the newest part of the chat after every step, or once as the turn ends, and acts when the answer reaches its threshold: it stops the turn, shows a notice, or tells the agent. A chat has at most 8. A monitor can watch the chat and its subagents; a subagent that a monitor stopped is reported to its parent as incomplete. A monitor can have a re-arm level, so it stops once and then stays quiet until the probability clears that level. Open Decision models and monitors… from the composer's + menu, or run biorouter session monitors.
  • The decide tool. The agent asks up to 16 questions about up to 200 pieces of text in one call, for example to screen hundreds of notes and read only the ones that matter. It comes from the Decisions capability, which is on by default.
  • Phase gates. In a plan with phases, a gate holds a phase, and every phase after it, until its questions pass. The agent cannot change, remove or skip a gate. A gate that names no decision model is judged by the chat's own model when the chat has none it may use or can reach, so a plan with gates works without decision models. Pass, skip or retry a gate in the app or with biorouter session gates.

A probability equal to the threshold passes. Monitors and the decide tool never fall back to the chat's own model. A chat's decision models count toward its privacy; see Private and public. biorouter decide asks a decision model one question from a terminal, and the decision models guide covers every setting.

Delegation and several chats

Subagents

Ask in plain language, for example “Have a subagent check the QC report while you draft the methods.” A subagent is a separate chat that runs one task and reports back to the chat that started it. Several can run one after another or in parallel. A subagent runs in the background and opens no tab unless you ask for one. In the desktop app it is listed in the chat summary: point at a row to preview its card, and choose the row to keep the card open. The card's Open in a tab opens the subagent as a tab, where you can read it as it works, type to steer it, and stop it. Closing the tab does not stop it. If you typed into it, the parent is told.

To have every new subagent open its own tab, turn on Settings → App → General → Open subagent tabs automatically, which is off by default; asking the agent for a tab also works. No tab opens when no desktop window is open, or when Never open tabs automatically is on. The subagent still runs.

  • A subagent runs on the model you name in your request. Otherwise it runs on the default worker model, if you set one (Settings → Models → Default model → Default worker model, or biorouter configure), and otherwise on the chat's own model. The default worker model never fails a spawn: when the privacy rules refuse it for a chat, or its provider is not set up, the chat's own model is used and the parent is told once. It replaced lead/worker mode; see Switch models.
  • It starts with the chat's own switches for extensions, built-in capabilities, skills and Contexts, and the agent can add or leave out extensions and skills for it. It has 25 turns (BIOROUTER_SUBAGENT_MAX_TURNS) and 5 minutes by default.
  • It cannot start subagents of its own, change the parent's extensions, or change schedules.
  • It never moves work across the privacy boundary. A public chat cannot start a subagent on a private model, and a private chat cannot start one on a public model. A public subagent is given no private data extensions, and the parent is told which were left out. A chat that a public decision model made public counts as public, so its subagents are public chats even when they run on its own private model. A spawn is refused when a monitor on it names a decision model the chat may not use. See What Biorouter refuses.
  • A chat at its usage limit, or any chat once the month is at its limit, starts no subagent, and a running subagent counts toward the limit of the chat that started it. See Loop limits.

The subagent tool is offered only when all five of these hold. If a request for a subagent gets an ordinary answer, check them in order.

  1. The permission mode is Autonomous (the default).
  2. The model's name does not start with gemini.
  3. The chat is not itself a subagent.
  4. At least one extension besides Workspace Control and Decisions is turned on. Neither of those two counts, because both are on by default.
  5. The chat is not an application that delegates to its own worker profiles.

Workspace Control

Workspace Control lets the agent work across your chats. It is on by default. To turn it off for new chats, use Settings → Chat → Capabilities in the app, or run biorouter configure in a terminal and choose Toggle Extensions, then workspace. The agent can:

  • open a new chat in a tab, a split pane or a new window. New tabs open in the background and start in your working folder.
  • list what is running, and read another chat as a summary, a transcript, its tool calls or a subagent's starting instructions. A public chat cannot read a private one.
  • send a prompt into another chat and wait for it to finish.
  • change another chat's extensions, skills, model or knowledge bases.

Some changes show a confirmation card in every permission mode: giving a chat an extension that can start programs, removing one that matters for security, switching its model provider, or adding a skill. The changed chat shows who changed what. The first time a private chat writes into a public chat, Biorouter shows you what it would send and asks first.

Steering a running turn

You do not have to wait for a turn to finish. A message you send while it runs waits in a queue above the text box. Each queued message has two buttons, named by their hover text:

  • Add now, “Add to the running turn without stopping”, adds the message to the running turn without stopping it. With the text box empty, Cmd+Enter (Ctrl+Enter on Windows and Linux) does the same for the first message in the queue.
  • Stop & send, “Stop the running turn, then send this”, stops the turn and sends the message as a new one.

An added message reaches the model at the next safe point. A running tool is never cut off for it. If an approval card is waiting, the message waits until you answer the card, because a message never answers a card. If the turn ends before the model reads it, the message stays in the chat marked as not answered. A message with attachments cannot be added to a running turn; it waits, or you can use Stop & send.

A browser opened with biorouter serve cannot add messages to a running turn, and neither can any other client of that service. Stop still works. Use the desktop app. biorouter session attach can add to a running turn only on a service started with a user action key; see Command line.

Goals: /goal

/goal keeps the agent working until a condition you can check is true.

/goal the notebook runs with no errors

Work starts at once. Each time the agent tries to finish, an evaluator reads the recent part of the chat and checks the condition. If it is not met, the evaluator's feedback goes back to the agent and the turn continues. After 20 evaluations, or when the evaluator gives nearly the same feedback 3 times in a row, the goal is dropped and the agent reports what it did, what is unfinished and what stands in the way.

/goal on its own shows the active goal, and /goal clear removes it. The goal is saved with the chat, so it survives a restart. Write the condition as an end state the agent can show, such as a file that exists or a test that passes.
