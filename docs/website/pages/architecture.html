Architecture

Biorouter has three layers: the interface you use, the agent that reasons and acts, and the extensions that give it tools. In the desktop app and the browser, the agent runs inside a background service, biorouterd.

Three layers

  • Interface. The desktop app, a browser opened with biorouter serve, or the biorouter command line. It shows the conversation and holds no reasoning of its own.
  • Agent. The loop that sends the conversation to a model, runs the tools the model asks for and returns the answer, together with chat history, the connections to model providers, and the running of workflows and schedules. See The agent loop.
  • Extensions. Servers that speak the Model Context Protocol (MCP), the open standard for giving a model tools. An extension that ships with Biorouter and one you install look the same to the agent. See Extensions and skills.

The background service

biorouterd serves the agent over local HTTP and WebSocket. The desktop app starts one for all of its windows. Schedules run inside it, so they run while it runs.

In the current release the service stops when you quit the app. From the next release, on macOS and Linux it keeps running after you quit, until the computer restarts; see Crew. On Windows it still stops when you quit. The shared service starts and connects automatically, without a daemon approval secret. After an update, opening the app replaces the older service; this can interrupt a running task or transfer.

The same release adds Crew, which connects the service to a lab workspace. The host runs the workspace with biorouter-crew on a shared Linux server, and each member's service reaches it over SSH through that member's own account on the server. Each member's agent still runs on their own computer, with their own model.

How each interface connects

InterfaceHow it reaches the agent
Desktop appThe app's main process starts biorouterd, and each window talks to it over HTTP and WebSocket, through a client generated from the service's OpenAPI description.
Browserbiorouter serve starts biorouterd, which serves the same interface from its own address. See Browser access.
Command line, on its ownBy default, biorouter session and biorouter run start the agent inside the terminal's own process. session list, export, rename and remove use the chat store directly. Nothing else needs to run.
Command line, livesession send, watch, attach and cancel talk to a running biorouterd, because a turn in progress exists only inside the service running it. See Sessions.
Command line, shared Next releaseWith --shared-daemon, biorouter session and biorouter run use the same background service as the desktop app, as biorouter crew does.

The app and the command line share one settings file, one credential store and one chat store, so a provider, an extension or a chat set up in one appears in the other. See Where files live.

The code

The backend is a Rust workspace. The desktop app is Electron, React and TypeScript, in ui/desktop.

PartCrate
Agent librarybiorouter holds the loop, model providers, chats, privacy, workflows and schedules, and capabilities such as Code Execution, Skills, Todo, Chat Recall and Workspace.
Background servicebiorouter-server builds biorouterd and its HTTP and WebSocket API.
Command linebiorouter-cli builds biorouter.
Bundled extensionsbiorouter-mcp holds Developer, Biorouter Copilot, Web & Documents, Memory, Auto Visualiser, Knowledge and Agent Drafter, plus the data, files and compute servers that built apps use.
Shell sandboxbiorouter-sandbox. See Shell sandbox.
Crew broker Next releasebiorouter-crew builds the biorouter-crew program for Linux.
Editor supportbiorouter-acp adds Agent Client Protocol support, so programs such as code editors can drive Biorouter through biorouter acp.
macOS promptbiorouter-authprompt shows the macOS authentication prompt that the background service cannot show itself.
Testsbiorouter-bench holds benchmarks, and biorouter-test holds integration tests.
