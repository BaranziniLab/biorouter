Models and providers

Biorouter runs local models, models your institution hosts, and public cloud models. Each chat has its own model, and you can change it; a private chat can switch only among private models.

The three tabs

Open Settings → Models → Configure providers. Every provider sits on one of three tabs, always in this order. Each tab opens with a heading and a note, quoted here in the app's own words.

Choose a provider's row, then Configure, and enter its credentials. Biorouter checks them with the provider before it saves them. In a terminal, biorouter configure lists the same providers as one list. Security explains where credentials are kept.

A chat becomes private once a turn runs on a private model. Private and public explains what that changes.

The model picker reads each provider's live list of models, so it is the place to see what you can use today. The defaults below are what Biorouter v{{LATEST_VERSION}} picks when you configure a provider without naming a model. An existing setup keeps its saved main model.

The memory figures are what the GPU can use; on a Mac, that is the unified memory. The two mixture of experts models use about 3B to 4B parameters per token, so they are fast once loaded, but they are large downloads. Any other model works too: give a Hugging Face spec such as owner/repo:Q4_K_M as the model name. To download a model before you need it:

biorouter models local pull gemma4-12b
biorouter models local list

The context window is sized to your memory (128k tokens at 64 GiB or more, 64k at 16 GiB or more, otherwise 32k). Set LLAMACPP_CONTEXT_SIZE to fix it. Thinking is off by default; LLAMACPP_ENABLE_THINKING=true turns it on.

Ollama (ollama) uses an Ollama server you already run on this computer. Pull a model (ollama pull qwen3) and select it. Default model: qwen3.

Local means this computer. If OLLAMA_HOST or LLAMACPP_EXTERNAL_HOST points at another machine, Biorouter treats that provider as public.

Versa API Azure takes your Versa API key and serves the UCSF ChatGPT models, only those UCSF has deployed. Versa API Bedrock takes your Versa access key ID and secret access key and serves the Anthropic models UCSF hosts on Amazon Bedrock.

UCSF researchers: use these two. Azure OpenAI and Amazon Bedrock on the Public tab are for your own Azure or AWS account, and they stay public even if you point them at a UCSF address.

Another institution's gateway appears on this tab once Biorouter recognizes its endpoint as private.

Public: AI agents on your subscription

The first section of the Public tab, “AI agents · your subscription”, holds Claude Code and Codex. The app says: “Biorouter drives a vendor CLI already installed and signed in on this machine; turns bill to that plan, not to an API key.” There is no key to paste, and Biorouter never sees the credential.

Agent and CLI nameDefault modelPlan
Claude Code

  1. Install the tool yourself Biorouter shows the command for your system but does not run it. The defaults above need claude 2.1.280 or newer and codex-cli 0.153.4 or newer. 
    # Claude Code on macOS and Linux
curl -fsSL https://claude.ai/install.sh | bash
# Claude Code on Windows
npm install -g @anthropic-ai/claude-code
# Codex
npm install -g @openai/codex@latest
  2. Sign in yourself Run claude auth login or codex login and sign in with your subscription.
  3. Choose it Pick it in Switch models, or choose Use Claude Code or Use Codex on its row.

The row shows where the tool stands: Not installed, Installed · not signed in, Signed in with an API key (the provider will not run, because turns would bill per token), Ready · signed in on your subscription, or Status unclear (choose Check again). If Biorouter cannot find the tool, set CLAUDE_CODE_COMMAND or CODEX_COMMAND to its path.

Biorouter's own tools reach the agent through Biorouter, so they still follow your permission mode and the privacy rules.

Both are public. A consumer plan carries no business associate agreement and no zero data retention agreement, so never use them with patient data.

Most take one API key. Its setting is named after the provider, and an environment variable of the same name works too: ANTHROPIC_API_KEY, OPENAI_API_KEY, GOOGLE_API_KEY, DEEPSEEK_API_KEY, GROQ_API_KEY, INCEPTION_API_KEY, MISTRAL_API_KEY, MOONSHOT_API_KEY, OPENROUTER_API_KEY, VENICE_API_KEY, XAI_API_KEY, XIAOMI_MIMO_API_KEY and ZAI_API_KEY. The others sign in differently:

  • Amazon Bedrock and AWS SageMaker TGI (listed in the app as Amazon SageMaker TGI) use your AWS profile or credentials, including SSO. SageMaker also needs SAGEMAKER_ENDPOINT_NAME.
  • Azure OpenAI needs your endpoint and deployment name, with a key or your Azure sign in.
  • Databricks needs the workspace host, with a token or OAuth. Snowflake needs the account host and a token.
  • GCP Vertex AI needs GCP_PROJECT_ID and GCP_LOCATION, with a service account or application default credentials.
  • GitHub Copilot signs in with a device code; there is no key.
  • LiteLLM needs your gateway's address and key.
  • Tetrate Agent Router Service opens a browser sign in, or takes TETRATE_API_KEY.

The SageMaker TGI and LiteLLM defaults are placeholders: the model is whatever your endpoint or gateway serves. Run biorouter models providers for the list on your computer and biorouter models list <provider> for a provider's models.

Add a custom provider

Any endpoint that speaks the OpenAI, Anthropic or Ollama API can be added.

  1. Open the form On the Public tab, choose Add custom provider at the end of the API providers.
  2. Describe the endpoint Pick the Provider Type (OpenAI Compatible, Anthropic Compatible or Ollama Compatible), then enter a Display Name, the API URL, the API Key, and the Available Models as a comma separated list. Tick whether it streams responses.
  3. Save The provider appears on the Public tab and in the model picker from then on.

Custom providers are listed as public, because Biorouter cannot verify where a custom endpoint points. One exception: an Ollama Compatible provider on this computer (localhost) runs as private, so its chats become private. An OpenAI Compatible or Anthropic Compatible provider stays public even on localhost; ticking This is a local model (no auth required) only removes the API key.

Switch models

In a chat. Choose the model chip under the message box, then a provider and model in Switch models. The change applies to that chat only. Tick Also use for new chats to make it the model new chats start on. A private chat lists public models as unavailable; see Private and public.

In a terminal. biorouter models set changes the default provider and model, and the same flags on biorouter session or biorouter run change them for one chat. Name only a provider other than your default, and it runs its own default model:

biorouter models set --provider ollama --model qwen3
biorouter session --provider llamacpp --model gemma4
biorouter run --provider versa_azure -t "Summarize ./notes.md"

In a workflow. A workflow can name its own model, so everyone who opens it starts on that model if they have that provider set up:

settings:
  biorouter_provider: llamacpp
  biorouter_model: gemma4-12b

Lead and worker. Set BIOROUTER_LEAD_MODEL (and BIOROUTER_LEAD_PROVIDER if it is another provider) to start each chat on a lead model for its first turns, three by default, before your default model takes over. Biorouter goes back to the lead when the worker fails repeatedly. Both models see the whole chat, so the pair counts as private only when both are private.
