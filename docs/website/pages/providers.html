Models and providers

Biorouter runs local models, models your institution hosts, and public cloud models. Each chat has its own model, and you can change it; a private chat can switch only among private models.

The three tabs

Open Settings → Models and choose Manage… beside Providers. Every provider sits on one of three tabs, always in this order. A one line note under the tabs gives the tab's privacy, quoted here in the app's own words.

TabHoldsThe note under the tab
LocalLlama Server, Ollama“Private because inference runs on this machine. Nothing leaves it.”
InstitutionalUCSF's Versa API Azure and Versa API Bedrock“Private because Biorouter recognizes this institutional gateway endpoint.”
PublicClaude Code and Codex, then the API providers“Public. Biorouter can't verify where this account's endpoint points, even one your institution pays for.”

Choose a provider's row, then Configure, and enter its credentials. Biorouter checks them with the provider before it saves them. In a terminal, biorouter configure lists the same providers as one list. Security explains where credentials are kept.

A chat becomes private once a turn runs on a private model. Private and public explains what that changes.

The model picker reads each provider's live list of models, so it is the place to see what you can use today. The defaults below are what Biorouter picks when you configure a provider without naming a model. The newest release is v{{LATEST_VERSION}}; where a default changed after v1.92.1, the page names both. An existing setup keeps its saved main model.

Local

Llama Server (llamacpp) comes with the desktop app and needs no setup and no key. Choose a model, then Download & run. The model downloads once, or starts from a copy already on your computer; after that, nothing leaves your computer.

Model and CLI nameDownloadNotes
Qwen3.8 27B
qwen3.8-27b		19 GBDefault on every machine after v1.92.1
Gemma 4 31B
gemma4-31b		18 GBGoogle's own 4-bit build

In v1.92.1 and earlier, Llama Server offers Gemma 4 and Qwen3.6 models and picks one by memory: Gemma 4 E4B (gemma4) below 64 GB, Gemma 4 12B (gemma4-12b) at 64 GB or more. After v1.92.1, a model name from an earlier version, such as either of those, runs Qwen3.8 27B.

Both models in the table need 32 GB of memory the GPU can use. Choose a computer for local models says what to expect at each size. Any other model works too: give a Hugging Face spec such as owner/repo:Q4_K_M as the model name. To download a model before you need it:

biorouter models local pull qwen3.8-27b
biorouter models local list

The context window is sized to your memory. After v1.92.1 it is 128k tokens at 48 GB or more, otherwise 64k; in v1.92.1 and earlier, 128k at 64 GB or more, 64k at 16 GB or more, otherwise 32k. Set LLAMACPP_CONTEXT_SIZE to fix it. Thinking is off by default; LLAMACPP_ENABLE_THINKING=true turns it on.

Ollama (ollama) uses an Ollama server you already run on this computer. Use Ollama 0.32.12 or later, which qwen3.8:27b needs, pull a model (ollama pull qwen3.8:27b) and select it. Default model: qwen3.8:27b after v1.92.1, qwen3 in v1.92.1 and earlier. Biorouter also supports gemma4:31b. Other models may write their tool calls as text instead of making them. Biorouter sets the context window it needs; OLLAMA_NUM_CTX overrides it.

Local means this computer. If OLLAMA_HOST or LLAMACPP_EXTERNAL_HOST points at another machine, Biorouter treats that provider as public. An Ollama cloud model is public too, even on this computer's Ollama, because Ollama answers it from ollama.com.

Choose a computer for local models

A local model runs in the memory the GPU can use. On a Mac with Apple silicon, that is the Mac's unified memory, and three things must fit in it at once: the model (about 22 to 25 GB for either model above, with its context window), Biorouter itself, and the data you are working on. On Windows or Linux, it is the graphics card's own memory, not the computer's RAM, and the model must fit there.

Memory the GPU can useWhat to expect
Under 32 GBNot recommended. The models are still offered, with a warning, but may fail to load or run very slowly.
32 GBThe minimum. The models run, with a 64k context window and less room for other apps.
48 GBRecommended. Llama Server uses a 128k context window (Ollama from 64 GB), so a chat holds more before it is summarized.
64 to 128 GBFor large datasets, or other demanding work running at the same time.

An Intel Mac, or any computer without a fast GPU, is slow whatever its memory, because the model runs on the processor: a few tokens per second, and many minutes before each chat's first reply. On Linux, the Llama Server that comes with Biorouter also runs on the processor, so use Ollama with GPU support there.

Each model needs about 20 GB of free disk space.

The first reply in a chat is the slowest, because the model first reads 31,000 or more tokens of Biorouter's instructions and tools. On an M4 Max, Qwen3.8 27B takes about 2.5 minutes for that; a chip with fewer GPU cores, such as a Pro or base M chip, takes longer. If a reply times out, raise OLLAMA_TIMEOUT or LLAMACPP_TIMEOUT (in seconds), or turn off extensions the chat does not need so the prompt is shorter.

The first section of the Public tab, “AI agents · your subscription”, holds Claude Code and Codex. The app says: “Biorouter drives a vendor CLI already installed and signed in on this machine; turns bill to that plan, not to an API key.” There is no key to paste, and Biorouter never sees the credential.

  2. Sign in yourself Run claude auth login or codex login and sign in with your subscription.
  3. Choose it Pick it in Switch models, or choose Use Claude Code or Use Codex on its row.

The row shows where the tool stands: Not installed, Installed · not signed in, Signed in with an API key (the provider will not run, because turns would bill per token), Ready · signed in on your subscription, or Status unclear (choose Check again). If Biorouter cannot find the tool, set CLAUDE_CODE_COMMAND or CODEX_COMMAND to its path.

Biorouter's own tools reach the agent through Biorouter, so they still follow your permission mode and the privacy rules.

Both are public. A consumer plan carries no business associate agreement and no zero data retention agreement, so never use them with patient data.

Most take one API key. Its setting is named after the provider, and an environment variable of the same name works too: ANTHROPIC_API_KEY, OPENAI_API_KEY, GOOGLE_API_KEY, BASETEN_API_KEY (after v1.93.2), DEEPSEEK_API_KEY, GROQ_API_KEY, INCEPTION_API_KEY, MISTRAL_API_KEY, MOONSHOT_API_KEY, OPENROUTER_API_KEY, VENICE_API_KEY, XAI_API_KEY, XIAOMI_MIMO_API_KEY and ZAI_API_KEY. The others sign in differently:

  • Amazon Bedrock and AWS SageMaker TGI (listed in the app as Amazon SageMaker TGI) use your AWS profile or credentials, including SSO. SageMaker also needs SAGEMAKER_ENDPOINT_NAME.
  • Azure OpenAI needs your endpoint and deployment name, with a key or your Azure sign in.
  • Databricks needs the workspace host, with a token or OAuth. Snowflake needs the account host and a token.
  • GCP Vertex AI needs GCP_PROJECT_ID and GCP_LOCATION, with a service account or application default credentials.
  • GitHub Copilot signs in with a device code; there is no key.
  • LiteLLM needs your gateway's address and key.
  • Tetrate Agent Router Service opens a browser sign in, or takes TETRATE_API_KEY.

The SageMaker TGI and LiteLLM defaults are placeholders: the model is whatever your endpoint or gateway serves. Run biorouter models providers for the list on your computer and biorouter models list <provider> for a provider's models.

Add a custom provider

Any endpoint that speaks the OpenAI, Anthropic or Ollama API can be added.

  1. Open the form On the Public tab, choose Add custom provider at the end of the API providers.
  2. Describe the endpoint Pick the Provider Type (OpenAI Compatible, Anthropic Compatible or Ollama Compatible), then enter a Display Name, the API URL, the API Key, and the Available Models as a comma separated list. Tick whether it streams responses.
  3. Save The provider appears on the Public tab and in the model picker from then on.

Custom providers are listed as public, because Biorouter cannot verify where a custom endpoint points. One exception: an Ollama Compatible provider on this computer (localhost) runs as private, so its chats become private. An OpenAI Compatible or Anthropic Compatible provider stays public even on localhost; ticking This is a local model (no auth required) only removes the API key.

Switch models

In a chat. Choose the model chip in the composer, then Change model…, then a provider and model in Switch models. The change applies to that chat only. Tick Also use for new chats to make it the model new chats start on. A private chat lists public models as unavailable; see Private and public.

In a terminal. biorouter models set changes the default provider and model, and the same flags on biorouter session or biorouter run change them for one chat. Name only a provider other than your default, and it runs its own default model:

biorouter models set --provider ollama --model qwen3.8:27b
biorouter session --provider llamacpp --model gemma4-31b
biorouter run --provider versa_azure -t "Summarize ./notes.md"

In a workflow. A workflow can name its own model, so everyone who opens it starts on that model if they have that provider set up:

settings:
  biorouter_provider: llamacpp
  biorouter_model: qwen3.8-27b

Lead and worker. Set BIOROUTER_LEAD_MODEL (and BIOROUTER_LEAD_PROVIDER if it is another provider) to start each chat on a lead model for its first turns, three by default, before your default model takes over. Biorouter goes back to the lead when the worker fails repeatedly. Both models see the whole chat, so the pair counts as private only when both are private.
