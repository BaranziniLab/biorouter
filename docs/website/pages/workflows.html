Workflows and scheduling

A workflow is one file that starts a chat with the same instructions and tools, and optionally the same model, every time. Send it to a colleague to run on their own data, or let the scheduler run it for you.

A workflow file

A workflow is written in YAML (recommended) or JSON. It needs a title, a description, and instructions or a prompt (or both). Save this as review.yaml:

version: "1.0.0"
title: Weekly cohort review
description: Counts new enrollments
instructions: Report counts, not records.
prompt: Summarize this week's enrollments.

Running it starts a new chat with those instructions. The desktop app puts the prompt in the text box for you to send; the command line and the scheduler send it for you. Use .yaml rather than .yml: the command line reads only .yaml and .json.

The fields

FieldWhat it holds
title, descriptionRequired. A short name and one line on what the workflow does.
instructionsThe system instructions for the chat. A workflow needs instructions, prompt or both.
promptThe first message.
parametersValues filled in at launch and inserted with {{ key }}. See Parameters.
extensionsThe extensions the chat needs. An env_keys list names the secrets an extension needs, and the command line asks for any that are missing.
skillsSkills whose instructions are added before the first model call. A skill that is not installed, or is switched off in the chat, stops the run with an error. A bundle name adds every skill in the bundle.
knowledge_basesvisible: the ids of the bases the chat may search. default: the base it writes to.
settingsbiorouter_provider, biorouter_model and temperature, for this workflow only.
activitiesButtons shown when the workflow opens in the desktop app. An entry that starts with message: is shown as a note above them.
responseA json_schema the final answer must match. The validated JSON is printed as the last line of output.
retrychecks run after the chat finishes (shell, file_exists, output_contains, json_schema), with max_retries and an optional on_failure command. A failed check starts the run again from the beginning.
sub_workflowsOther workflow files this one can call as tools, each with a name, a path and fixed values. Experimental.
authorcontact and metadata about who wrote it.
versionThe file format version. Defaults to "1.0.0".

The text fields are templates:

  • {{ workflow_dir }} is the folder that holds the file, so a workflow can point at files that travel with it.
  • {% extends "base.yaml" %} builds one workflow on another.

The full reference is the workflow schema.

Parameters

Parameters make one workflow serve many studies. Each has a key, an input_type, a requirement and a description. Add these to review.yaml and replace its prompt:

parameters:
  - key: study
    input_type: string
    requirement: optional
    default: MS-2041
    description: Study name
  - key: format
    input_type: select
    requirement: optional
    default: markdown
    options: [markdown, csv]
    description: Output format
prompt: Summarize enrollments in {{ study }} as {{ format }}.
RequirementMeaning
requiredMust be given at launch. Cannot have a default.
optionalMust have a default.
user_promptAsked for when no value is given.

The input types are string (the default), number, boolean, date, select, which needs options, and file, which reads the file at the path given and inserts its contents. A file parameter cannot have a default. Every {{ key }} in the file must match a parameter, and every parameter must be used; Biorouter checks this when it loads the workflow.

Save, run and share

Save a chat as a workflow

  1. Open the chat summary In the chat you want to keep, choose the chat summary button in the chat header, then Make workflow.
  2. Read the draft Biorouter drafts the title, instructions and prompt from the conversation and fills in the chat's extensions, skills, knowledge bases and model. Edit what you need.
  3. Save Choose Create workflow. The workflow appears under Workflows in the sidebar.

You can also ask in the chat, for example “Turn this chat into a workflow.” The agent shows you the workflow and asks you to approve it before anything is saved. Saved workflows live in ~/.config/biorouter/workflows/, where the app and the command line both find them.

Run a workflow

In Workflows, choose Use workflow, or Launch workflow, then Open in new window. The first time you run a workflow, Biorouter shows its title, description and instructions; choose Trust and execute to go on. If it has parameters, fill them in and choose Start workflow. Add slash command gives a workflow a shortcut you can type in any chat.

biorouter run --workflow review.yaml --params study=MS-2107
biorouter workflow validate review.yaml    # check that it loads
biorouter workflow install review.yaml     # add it to the library
biorouter workflow list

Share a workflow

Send the file, or send a link. In Workflows, the Share workflow menu has Copy deeplink, Copy YAML and Export to file. The person who receives a file adds it with Import workflow, or runs it with the biorouter run command above. From a terminal, make a link that fills in parameters for them:

biorouter workflow deeplink review.yaml --param study=MS-2107

Opening the link opens Biorouter with the workflow loaded. A link encodes the workflow into a biorouter://workflow address, plus any parameter values you gave it. It does not carry files that sit next to the workflow, so send those with the file.

Share the method, not the data

A workflow carries instructions, not records. The file holds the steps, the parameters and the names of the extensions, skills, knowledge bases and model it needs. Biorouter leaves out API keys, memory and the conversation history; the file holds only the text you write or approve.

  • Each run is the recipient's own chat. It starts on their computer, with their extensions, their credentials and their models, under their institution's agreements. It follows the same privacy rules as any other chat: if it uses a private model or a private data extension, it becomes Private. See Private and public.
  • Data is read where it lives. A file parameter reads a file on the computer of the person running the workflow, when the run starts.
  • Results stay with the recipient. Nothing flows back to you. They share what they choose to share.
  • Edits do not travel back. A recipient's changes stay in their copy, and your file is unchanged.

Read a workflow before you share it. It holds whatever text is in it. A draft made with Make workflow is written from the conversation, so remove any values that came from your data.

Scheduling

A schedule runs a workflow at set times with nobody watching. Each run is a new chat of its own, saved to history. Schedules run in the background while a Biorouter background service runs, such as the desktop app's or the one biorouter serve starts. They are kept in schedule.json in Biorouter's data folder, so they survive a restart, and every running service follows that file. A run that comes due while one of your chats is running a turn, or while the provider is limiting requests, is skipped and runs at its next time.

The Scheduler page

  1. Open Scheduler Choose Scheduler in the sidebar, then New schedule. From Workflows, the clock button (Add schedule) does the same for one workflow.
  2. Fill in the schedule Give it a name, choose the workflow file, and set when it runs.
  3. Create it Choose Create schedule.

Each schedule shows when it runs in words and how its last run went. From its row you can edit, pause, resume or delete it. Its page has Run now and lists every chat the schedule has run. Biorouter includes one schedule, Daily Meditation, which updates the Soul knowledge base from your recent chats at 3:00 each night; see Knowledge bases.

From a chat: /schedule and /loop

/schedule @daily Summarize new preprints on remyelination
/schedule "0 9 * * 1" Draft the weekly lab update
/loop 10m Check whether the alignment job has finished
  • /schedule <when> <prompt> runs a prompt until you remove it. When is an interval (5m, 2h, 1d), @hourly, @daily, @weekly, @monthly, or a cron expression in quotes. /schedule list shows them all. /schedule remove, run, pause, unpause and sessions take a schedule id.
  • /loop <interval> <prompt> is for short polling: 30s, 5m, 2h or 1d. A run that is still going when the next is due is skipped, and the loop stops itself after 100 runs. /loop lists loops, and /loop stop <id> or /loop stop all ends them.

When the agent schedules something

You can ask the agent, for example “Run the cohort review every Monday at 8am.” Every change the agent makes to a schedule shows an approval card first: creating one, running it now, pausing or resuming it, deleting it, or stopping a run. The card appears in every permission mode, Autonomous included. It says in words when the job will run, which workflow it runs and how, and the card for a new schedule shows the whole workflow. Only a person can approve it. Listing and reading schedules asks nothing.

From the command line

biorouter schedule add \
  --schedule-id review-weekly \
  --cron "0 8 * * 1" \
  --workflow-source ./review.yaml
biorouter schedule list
biorouter schedule run-now --schedule-id review-weekly
biorouter schedule sessions --schedule-id review-weekly
biorouter schedule remove --schedule-id review-weekly
biorouter schedule cron-help    # cron examples

--cron takes five fields (minute, hour, day of month, month, day of week), or six with seconds first, in this computer's local time; "0 8 * * 1" is every Monday at 8:00. The schedule keeps its own copy of the workflow as it was when you added it.

When this terminal cannot reach a Biorouter service, which is always the case next to the desktop app and in an agent's shell, the command writes the schedule file itself, and a running service picks it up within 60 seconds. In that case add, remove and run-now ask you to confirm at the terminal, and refuse when there is no terminal to ask, so an agent's shell cannot add a schedule on its own. When BIOROUTER_SERVER__SECRET_KEY and BIOROUTER_PORT point at a running service, that service makes the change without asking, or refuses it when the schedule would run on a private model.

What a scheduled run needs

  • A prompt, since nobody is there to type the first message.
  • A value for every parameter without asking: use optional parameters with defaults, and no user_prompt ones.
  • The model's credentials, the extensions and the files the workflow uses, all in place on this computer when the run starts. A workflow that works in a chat can still fail on a schedule if it depends on something only you supply there.

A failed run is recorded on the schedule, and the schedule runs again at its next time.
