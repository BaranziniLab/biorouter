Command line

The biorouter command runs the same agent as the desktop app, from a terminal. It shares your settings, chats and extensions with the app.

The desktop app includes the command; Getting started shows how to put it on your PATH. On a Linux server, install the biorouter-cli package instead. Add --help to any command to see its flags.

Everyday use

Choose a model

Run biorouter configure once before anything else. The first time, it offers a local model (Llama Server), signing in with OpenRouter or Tetrate, or setting up a provider by hand. Run it again and choose Configure Providers to change the model, or Biorouter settings for the mode, tool permissions and turn limit. It needs a terminal, so a script uses models set instead and passes the provider's key in its environment variable, such as OPENAI_API_KEY.

biorouter configure
biorouter models set --provider PROVIDER --model MODEL

Chat in the terminal

Run biorouter with no command to start a chat. On a real terminal it opens a full screen chat. Set BIOROUTER_CLI_CLASSIC to any value for the older line by line prompt, which Biorouter also uses when the output is not a terminal. When no settings exist yet, biorouter runs configure first.

# A new chat, or a new chat with a name
biorouter
biorouter session -n gwas-followup

# Continue the last chat, or a named one with its history
biorouter session --resume
biorouter session --resume -n gwas-followup --history
KeyIn the full screen chat
EnterSend. While the agent is answering, the message waits and is sent when the turn ends.
Shift+EnterNew line. Ctrl+J also works.
Ctrl+CStop the running turn. With nothing running, clear the text; on an empty line, leave. Ctrl+D also leaves.

Sessions

Every chat is a session in one local store that the app and the command line share. The session commands come in two kinds.

biorouter session list --limit 10
biorouter session export -n gwas-followup -o gwas-followup.md
biorouter session rename -n gwas-followup --new-name hla-loci
biorouter session remove --session-id 20260929_3

The live commands need a biorouterd this terminal can reach, on BIOROUTER_PORT (3000 unless set) with the same BIOROUTER_SERVER__SECRET_KEY it was started with. The desktop app's own service picks a random port and a new key at every launch and publishes neither, so an open app does not count. Start a service you control:

# Terminal 1: a service with a key you choose
BIOROUTER_SERVER__SECRET_KEY=KEY biorouterd agent

# Terminal 2: the same key
export BIOROUTER_SERVER__SECRET_KEY=KEY
biorouter session send 20260929_2 "Summarize your findings"
biorouter session watch 20260929_2 --follow
biorouter session attach 20260929_2
biorouter session cancel 20260929_2

On a chat that is running, use attach, not session --resume: resuming opens a second agent on the same chat. send --no-wait returns at once, but the service stops a turn that nothing has been attached to for five minutes, so leave it off for long turns. A service started by hand has no user action key, so it refuses to steer a turn already running and says so; stopping still works.

Run one task

biorouter run sends one request and exits. Use it in scripts, on a cluster or in CI.

biorouter run -t "Summarize the QC report in ./qc.html"
cat plan.md | biorouter run -i -
biorouter run --workflow variants.yaml --params gene=HLA-DRB1
biorouter run --workflow variants.yaml --explain

For an unattended run, pin the model and set a limit, as below. The flags are under Reference, and the exit code says why a run stopped (Exit codes).

biorouter run --no-session --provider llamacpp --model gemma4 \
  --output-format json --max-turns 10 \
  -t "Check samples.csv for duplicate sample IDs"

Workflows and schedules

A workflow is a saved recipe for a chat, and a schedule runs one on a cron expression. Workflows and scheduling explains how to write both.

biorouter workflow validate variants.yaml
biorouter workflow install variants.yaml
biorouter workflow open variants -p gene=HLA-DRB1
biorouter workflow deeplink variants -p gene=HLA-DRB1

biorouter schedule add --schedule-id review-weekly \
  --cron "0 8 * * 1" --workflow-source ./review.yaml
biorouter schedule list
biorouter schedule run-now --schedule-id review-weekly
biorouter schedule sessions --schedule-id review-weekly -l 10
biorouter schedule remove --schedule-id review-weekly

deeplink prints a link that opens the workflow in the desktop app. --cron takes five fields, six with seconds first, or @hourly, @daily, @weekly or @monthly; schedule cron-help prints examples. A job keeps its own copy of the workflow, so later edits to the file do not change it. --id is short for --schedule-id.

Jobs run in the background while a Biorouter service is running. When this terminal can reach a running service (the same two variables as the live session commands), that service makes the change. Otherwise add and remove ask you to confirm and write the schedule file themselves, and a running Biorouter, the desktop app included, picks up the change within 60 seconds. run-now asks, then runs the job once in this terminal. Because a job is an agent that runs unattended, none of them goes ahead without a person at a terminal.

Fix a missing tool

biorouter doctor checks the tools extensions depend on (Git and uv are required; Python 3, Node.js, the AWS CLI, llama-server and Rust are optional), whether biorouter is on your PATH, the local model server, and whether a newer release exists. --fix opens a chat that already knows the failing tool and this machine, so the agent can repair it with you. With no tool named, it takes the first missing required one. --format json prints the checks for a script, and --no-update skips the release check.

biorouter doctor
biorouter doctor --fix
biorouter doctor --fix uv

Browser access

biorouter serve shows the desktop app's interface in a web browser. Use it on a Linux server, in a container, or on a machine you reach over SSH. It starts its own biorouterd, which serves the interface and its API from one address.

Set it up

  1. Install On a desktop computer, the app's command already includes serve. On a server, install the command line package. It puts biorouter and biorouterd in /usr/bin and the interface in /usr/share/biorouter/web. 
    # Debian, Ubuntu
sudo apt install ./biorouter-cli_*_amd64.deb

# Rocky, RHEL, Fedora
sudo dnf install ./biorouter-cli-*-1.x86_64.rpm
  2. Choose the model Run biorouter configure, as the account that will run serve. The browser cannot change the model later; see The model is fixed.
  3. Start it Run biorouter serve --open. It opens your browser and stays in the foreground. Without --open, copy the whole address from these lines of its output: 
      Biorouter is serving at

      http://127.0.0.1:8765/?t=1f4c9e02...

Ctrl+C stops serve and its service and frees the port. Past chats show in both serve and the desktop app, since both read the same chat store, but a turn running in one does not show in the other.

FlagWhat it does
--hostThe address to listen on, 127.0.0.1 by default. An address other machines can reach requires a token.
--portThe port, 8765 by default (-p).
--openOpen a browser when the server is ready, without putting the token on a command line.
--tokenUse a fixed token instead of a new one. Other accounts can read it in ps; The access token has a safer way.
--no-tokenServe with no token. Refused unless the address is local.
--web-dirThe folder holding the built interface, when serve cannot find it. It must contain an index.html. BIOROUTER_SERVE_UI does the same.
--computer-use-approvalSet a Biorouter Copilot approval key of at least 16 characters, typed at the terminal. It is never saved.

The access token

  • The address ends in ?t= and a token. Unless you set a fixed one, the token is new on every launch and shown once.
  • Opening the address gives the browser a cookie and removes the token from the address bar.
  • The token is not used up. Anyone with the address can open it until serve stops, so stopping serve is how you revoke it.
  • To keep one address across restarts, set BIOROUTER_BROWSER_TOKEN to a long random value, for example from openssl rand -hex 32.

Reach it from another machine

For one person, keep the local address and forward the port over SSH, then open the printed address in a browser on your own computer.

ssh -N -L 8765:127.0.0.1:8765 user@remote-host

To serve other machines on the network, listen on every address. A token is then required, and serve prints a second address that other machines can use.

biorouter serve --host 0.0.0.0

Exposing the port exposes the agent. The browser can do what the desktop app does: run shell commands, read and write files, and spend your model credits, on the serving machine, as the account that started serve. There is one token and no user accounts, and the connection is plain HTTP. Beyond a trusted lab network, put a reverse proxy with TLS in front of it and limit who can reach the port.

For a service that restarts on its own, keep the fixed token in an environment file that only the service account can read. The headless Linux guide has a systemd unit.

The model is fixed

A browser session cannot change its model or provider. This is deliberate. A chat that has used a private model may never reach a public one, and the desktop app can switch models only because it holds proof that a person asked. A browser tab cannot hold that proof.

So the model is chosen once, at the terminal, and every chat in that serve runs on it: private for its whole life on a private model, public on a public one. A private chat started in the desktop app opens in the browser only when the host's model is private too. To change the model, stop serve, run biorouter configure and start it again.
